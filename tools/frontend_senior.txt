## JavaScript · Engine & memory

How does V8 run JavaScript, and why does "shape stability" matter?
Ignition interprets bytecode, TurboFan compiles hot functions using inline caches; objects with a stable hidden class (same properties, same order) stay fast.
V8 parses to bytecode and runs it in the Ignition interpreter while collecting type feedback. Hot functions go to the optimizing compiler, TurboFan, which relies on inline caches: it assumes an object keeps the same hidden class. If I add properties in different orders or switch types, the code deoptimizes. So I initialize objects with the same shape and avoid `delete` on hot paths.
Ignition интерпретирует байткод, TurboFan оптимизирует горячие функции через inline caches; стабильная форма объектов (одинаковые поля в одном порядке) не даёт деоптимизации.

How does garbage collection work in V8, and what is a generational heap?
Mark-and-sweep with two generations: a small young space collected often by Scavenger, and an old space collected rarely by the major, incremental and concurrent GC.
V8 splits the heap into a young generation and an old generation. Most objects die young, so the Scavenger copies survivors between two semi-spaces cheaply and often. Objects that survive twice are promoted to old space, which is collected with mark-sweep-compact, done incrementally and partly on background threads to avoid long pauses. Allocation pressure, not just leaks, is what makes GC visible as jank.
Куча делится на молодое поколение (частый дешёвый Scavenger) и старое (редкий mark-sweep-compact, инкрементально и в фоне). Давление аллокаций само по себе даёт фризы.

Name the typical memory leaks in a SPA and how you find them.
Forgotten listeners and timers, closures holding big data, detached DOM nodes, caches without eviction, global stores that only grow; find them with heap snapshots and allocation timelines.
The usual leaks are event listeners or intervals that are never removed, closures that keep a large array alive, DOM nodes removed from the page but still referenced from JS, caches and maps that never evict, and a global store that accumulates every page ever visited. In DevTools I take two heap snapshots, repeat the action, compare, and look at retained size and the retainers tree. The allocation timeline shows which code allocates during the action.
Утечки: неснятые слушатели и таймеры, замыкания с большими данными, отвязанные DOM-узлы, кэши без вытеснения, растущий глобальный стор. Ищу через сравнение heap snapshots и retainers.

WeakMap, WeakSet, WeakRef and FinalizationRegistry — when do you use them?
WeakMap keys don't keep objects alive, so it's for metadata and caches tied to object lifetime; WeakRef and FinalizationRegistry are last-resort tools for caches, never for logic.
A WeakMap lets me attach data to an object without preventing its collection, which is perfect for private data or memoizing by object identity. WeakRef gives a reference that may become empty, and FinalizationRegistry runs a callback after collection. Collection timing is unpredictable, so I use those two only for optional caches, never for correctness.
WeakMap не удерживает ключи — для метаданных и кэшей по объекту. WeakRef и FinalizationRegistry непредсказуемы по времени, только для необязательных кэшей.

structuredClone vs JSON.parse(JSON.stringify()) vs a spread?
Spread is shallow; the JSON trick drops undefined, Dates, Maps, functions and cycles; structuredClone deep-copies most built-ins and cycles but not functions or DOM nodes.
Spread copies only the first level. The JSON round-trip loses undefined, turns Dates into strings, can't handle Map, Set, BigInt or circular references. structuredClone is the proper deep copy: it handles cycles, Dates, Maps, Sets, typed arrays, but throws on functions, symbols and DOM nodes, and it drops prototypes, so class instances come back as plain objects.
Spread — поверхностно; JSON теряет undefined, Date, Map, циклы; structuredClone — настоящая глубокая копия, но не функции, не DOM, прототипы теряются.

What is the difference between the call stack, the heap and the task queues?
Stack holds execution frames, heap holds objects, queues hold callbacks waiting for the event loop; a stack overflow is deep recursion, a leak is heap growth, jank is a long task on the stack.
The call stack is the sequence of currently executing frames. The heap is where objects live and what the GC manages. Task queues hold callbacks the event loop will run when the stack is empty. Each problem has its own symptom: deep recursion overflows the stack, retained objects grow the heap, and a long synchronous task blocks the loop and freezes the UI.
Стек — кадры выполнения, куча — объекты, очереди — колбэки для event loop. Переполнение стека, рост кучи и долгая задача — три разные проблемы.

## JavaScript · Async deep dive

In what order do microtasks, macrotasks, requestAnimationFrame and rendering run?
After each macrotask the whole microtask queue drains; then, if it's time for a frame, rAF callbacks run and the browser renders; new macrotasks wait until the next loop turn.
One macrotask runs, then every queued microtask, including ones added while draining, so a microtask loop can starve rendering. When a frame is due the browser runs requestAnimationFrame callbacks, then style, layout and paint. setTimeout(0) lands in a later turn, so it's after rendering may have happened. That's why measuring layout then changing it inside rAF is safe, and why an infinite promise chain freezes the page.
Макрозадача → все микрозадачи (даже новые) → при кадре rAF → рендер. Цикл микрозадач блокирует отрисовку; setTimeout(0) — уже следующий оборот.

What does async/await compile down to, and how many ticks does await cost?
A state machine over promises; `await` on a native promise takes one microtask tick, awaiting a non-promise also takes one, so code after await never runs synchronously.
An async function is desugared into a generator-like state machine where each await suspends and resumes via promise reactions. Since ES2019 awaiting a native promise costs a single microtask tick. The code after await always runs asynchronously, even for `await 42`. That matters for ordering tests and for understanding why `return await` inside try/catch is the only way to catch a rejection there.
Async/await — машина состояний над промисами; await стоит один microtask tick; код после await всегда асинхронный; внутри try/catch нужен return await.

How do you cancel an async operation in JavaScript?
Promises aren't cancellable; use AbortController: pass its signal to fetch, listeners and timers, check `signal.aborted` in loops, and clean up in the abort event.
Promises have no built-in cancel, so the standard is AbortController. I pass `controller.signal` to fetch, to addEventListener, and to my own async functions, where I check `signal.aborted` between steps or reject with signal.reason. In React I create a controller in the effect and abort it in the cleanup, which also kills race conditions between requests. `AbortSignal.timeout()` and `AbortSignal.any()` combine timeouts with user cancellation.
Промисы не отменяются; стандарт — AbortController: signal в fetch, слушатели, свои функции; в React abort в cleanup эффекта; AbortSignal.timeout/any для комбинаций.

What is an unhandled rejection, and how do you handle errors globally on the frontend?
A rejected promise with no handler by the end of the microtask checkpoint; catch it with `unhandledrejection` and `error` events, plus React error boundaries, and report to monitoring.
If a promise rejects and nothing attached a catch before the microtask queue drains, the browser fires `unhandledrejection`. I listen to that and to `window.onerror` for synchronous errors, send them to Sentry or similar with user and release context, and show a generic fallback. Render errors go through React error boundaries. Important detail: errors inside event handlers and async code don't reach boundaries, so the global handlers are the safety net.
Отклонённый промис без catch → unhandledrejection; плюс window.onerror и error boundaries, отправка в мониторинг. Ошибки в хендлерах и async до boundary не доходят.

Async iterators and generators — where do they help on the frontend?
Streams and pagination: `for await` over a ReadableStream, server-sent chunks or paged API results, with back-pressure and cancellation built in.
Async generators let me model a sequence that arrives over time: reading a fetch body as a stream, consuming SSE, or walking paginated API pages with `for await`. The consumer pulls, so I get natural back-pressure and can break out of the loop to stop fetching. They also make infinite scroll logic testable without React involved.
Асинхронные генераторы — потоки и пагинация: for await по ReadableStream, SSE, страницам API; естественный back-pressure и остановка через break.

Web Workers vs the main thread — what would you move and how?
CPU-heavy work (parsing, diffing, compression, image processing) goes to a worker via postMessage or Comlink, with Transferable objects to avoid copying; DOM stays on main.
Anything that takes more than tens of milliseconds and doesn't touch the DOM is a worker candidate: parsing a big JSON or CSV, diffing documents, encoding images, running search indexes. Communication is message passing, and I transfer ArrayBuffers instead of copying them. Libraries like Comlink turn it into async function calls. A SharedWorker or a service worker is a different thing: shared across tabs, or a network proxy.
В воркер — тяжёлые вычисления без DOM: парсинг, диффы, картинки, индексы. Общение через postMessage, передача ArrayBuffer без копирования, Comlink для удобства.

How do you implement retry with exponential backoff correctly?
Retry only idempotent requests and retryable errors (network, 429, 5xx), with jittered exponential delays, a max attempt count, honor Retry-After, and respect the abort signal.
A proper retry wrapper checks that the error is retryable: network failure, 429, 502, 503, 504, not a 400 or 401. Delays grow exponentially with random jitter to avoid thundering herds, and a Retry-After header wins when present. Non-idempotent POSTs need an idempotency key before they're safe to retry. The loop also stops when the AbortSignal fires so a navigated-away user doesn't keep hammering the API.
Ретраить только идемпотентное и ретраибельные ошибки (сеть, 429, 5xx), экспоненциальная задержка с джиттером, лимит попыток, Retry-After, отмена по signal, idempotency key для POST.

What's the difference between setTimeout, setInterval, requestAnimationFrame and requestIdleCallback?
setTimeout schedules a macrotask with a minimum delay; setInterval drifts and can pile up; rAF runs before the next paint at display rate; rIC runs in idle periods for low-priority work.
setTimeout delays are a minimum, clamped and throttled in background tabs. setInterval keeps firing even if the callback is slow, so I usually prefer a recursive setTimeout. requestAnimationFrame is tied to the display refresh and pauses in hidden tabs, which makes it right for animation and reading layout. requestIdleCallback gives me time slices when the browser is idle, good for analytics or prefetching, with a deadline I must respect.
setTimeout — минимальная задержка, троттлится в фоне; setInterval дрейфует; rAF — перед кадром, для анимаций и измерений; rIC — в простое, для неприоритетного.

How does fetch streaming work and when would you use it?
`response.body` is a ReadableStream; read chunks with a reader or `for await`, decode with TextDecoder, and render progressively, e.g. for AI token streams or large exports.
Instead of awaiting response.json(), I take response.body.getReader() and read chunks as they arrive, decoding with a TextDecoder in streaming mode. That lets me show partial content, like streamed LLM output or a long log, and start rendering a big list before the download finishes. The abort signal cancels the stream, and I always handle partial final chunks when splitting by lines.
response.body — ReadableStream: читаю чанки, декодирую TextDecoder, рендерю по мере поступления (стриминг ответа ИИ, большие выгрузки); отмена через signal.

## JavaScript · Language internals

What are iterators and the iterable protocol, and why does spread work on a Map but not on a plain object?
An iterable has `[Symbol.iterator]` returning an object with `next()`; Map, Set, arrays and strings implement it, plain objects don't, so spread, for-of and destructuring work only on iterables.
Anything with a `Symbol.iterator` method that returns `{ next() }` is iterable, and that's what for-of, spread in arrays, Array.from and destructuring consume. Map and Set implement it; plain objects don't, which is why `[...obj]` throws while `{...obj}` works, because object spread uses own enumerable keys, not the protocol. I can make my own data structures iterable with a generator method.
Итерируемое = есть Symbol.iterator с next(). Map/Set/массивы — да, объект — нет; поэтому [...obj] падает, а {...obj} работает через ключи.

Proxy and Reflect — what are they, and where are they used in real libraries?
Proxy intercepts operations on an object (get, set, has, deleteProperty…); Reflect gives the default behaviour; Vue 3 reactivity, MobX, Immer and Valtio are built on them.
A Proxy wraps a target and lets me trap operations: reads, writes, `in`, deletion, function calls. Reflect mirrors those operations so a trap can forward to the default behaviour. Vue 3 tracks dependencies by trapping `get` and triggers updates on `set`; Immer records mutations on a draft proxy and produces an immutable copy. The costs are performance on hot paths and that proxies can't be polyfilled or made transparent to identity checks.
Proxy перехватывает операции над объектом, Reflect даёт поведение по умолчанию. На этом стоят реактивность Vue 3, MobX, Immer. Минусы — скорость и непрозрачность.

What are Symbols for, beyond unique keys?
Well-known symbols hook into language behaviour: Symbol.iterator, asyncIterator, toPrimitive, hasInstance, toStringTag; Symbol.for creates a global registry key.
Symbols are collision-free property keys that are skipped by JSON and Object.keys. The well-known ones are protocol hooks: Symbol.iterator makes an object iterable, Symbol.toPrimitive controls coercion, Symbol.hasInstance customizes instanceof. Symbol.for registers a shared symbol across realms, which libraries use to mark their objects, like React's `$$typeof` on elements for safety against JSON-injected elements.
Символы — уникальные ключи, невидимые для JSON и keys; well-known символы — хуки протоколов (iterator, toPrimitive, hasInstance); Symbol.for — глобальный реестр.

How do ES modules differ from CommonJS at runtime, not just syntax?
ESM is statically analyzed, hoisted and asynchronous, exports are live bindings; CJS is synchronous, dynamic, exports a copied value; mixing them is where "default is undefined" bugs come from.
ES modules are linked before execution, so imports are resolved statically, cycles are handled via live bindings, and top-level await is possible. CommonJS `require` runs synchronously and returns whatever `module.exports` is at that moment. When bundlers or Node interop the two, a CJS module appears as a namespace object with a default property, which is where the "default is undefined" and dual-package hazards come from. Tree shaking needs the static ESM graph.
ESM — статический, асинхронный, живые привязки; CJS — синхронный, копия значения. Интероп даёт баги вида default undefined; tree shaking возможен только для ESM.

How do class fields, private fields and arrow methods interact with `this`?
Class fields are per-instance and initialized before the constructor body; `#private` is truly private and not on the prototype; an arrow field binds `this` but costs memory per instance and breaks prototype overriding.
Field initializers run per instance, in order, before the constructor body, with `this` already bound. `#name` fields are enforced by the engine, invisible to reflection, and checking `#x in obj` is a brand check. Arrow function fields capture `this` so they survive being passed as callbacks, but every instance gets its own copy and subclasses can't override them via the prototype. In React class components that trade-off is why bind-in-constructor and arrow fields both existed.
Поля инициализируются до тела конструктора; #private — настоящая приватность; стрелочные поля привязывают this, но копируются на каждый экземпляр и не переопределяются через прототип.

What is prototype pollution and how do you defend against it?
An attacker writes to `__proto__` via a recursive merge or deep set, changing every object; defend by rejecting `__proto__`, `constructor`, `prototype` keys, using Map or null-prototype objects, and updating libraries.
If code does a deep merge from untrusted JSON, a key like `__proto__` lets the input set properties on Object.prototype, so every object suddenly has `isAdmin: true` or a polluted `toString`. Defences are to block those three keys in merge and path-set utilities, keep user data in Map or `Object.create(null)`, freeze prototypes in sensitive code, and keep lodash-style libraries updated since they had exactly these CVEs.
Deep merge недоверенного JSON с ключом __proto__ меняет Object.prototype. Защита: блокировать __proto__/constructor/prototype, Map или null-прототип, обновлять библиотеки.

Explain getters/setters, Object.defineProperty and property descriptors.
Descriptors control writable, enumerable, configurable and accessor pairs; freeze and seal are built on them; frameworks used accessors for reactivity before Proxy.
Every property has a descriptor: data properties with value and writable, or accessors with get and set, plus enumerable and configurable flags. Object.freeze sets writable and configurable to false shallowly, which is why freezing a nested state is a recursion. Getters make computed values look like fields, and that's how Vue 2 and MobX observed changes before Proxies. A non-enumerable property is a way to hide helpers from JSON and spread.
Дескрипторы: value/writable или get/set, плюс enumerable и configurable. freeze поверхностный; геттеры дали реактивность до Proxy; non-enumerable скрывает от JSON и spread.

## TypeScript · Advanced types

Conditional types with `infer` — how do you extract a function's return or a promise's value?
`T extends (...a: any[]) => infer R ? R : never` pulls the return type; `T extends Promise<infer U> ? U : T` unwraps a promise; conditional types distribute over unions.
infer declares a type variable inside the extends clause and lets TypeScript solve for it. That's how ReturnType, Parameters and Awaited are implemented. A conditional type over a naked type parameter distributes across a union, so `Unwrap<A | B>` becomes `Unwrap<A> | Unwrap<B>`, which is usually what I want and occasionally what I have to prevent by wrapping in a tuple.
infer — переменная типа в extends; так устроены ReturnType, Parameters, Awaited. Условные типы распределяются по union; обернуть в кортеж, чтобы отключить.

Mapped and template literal types — give a practical example.
`{ [K in keyof T as \`on${Capitalize<K & string>}\`]: (v: T[K]) => void }` turns a props object into typed event handlers; remapping keys with `as` and key filtering are the power tools.
Mapped types iterate over keys of another type, and with the `as` clause I can rename or filter them. Combined with template literal types I can derive `onNameChange` from `name` or build typed route params from a path string like `/users/:id`. That removes duplication between an API schema and the handlers around it, and the compiler catches renames for free.
Mapped types перебирают ключи, as переименовывает/фильтрует, шаблонные литералы собирают имена: onNameChange из name, типизированные параметры роута из строки пути.

What is structural typing, and when does it bite you?
Types are compatible by shape, not by name; so two different IDs are interchangeable strings — branded types or classes with private fields restore nominal checks.
TypeScript compares types by their members, so anything with the right shape is assignable. That's flexible, but it means a `UserId` and an `OrderId` that are both strings swap silently. I fix that with branded types: `type UserId = string & { __brand: 'UserId' }` plus a constructor function. Excess property checks only apply to fresh object literals, which is another surprise of structural typing.
Типы совместимы по форме, не по имени: UserId и OrderId как string взаимозаменяемы. Решение — брендированные типы; проверка лишних полей работает только для литералов.

Variance: why is `Array<Dog>` assignable to `Array<Animal>` and why is that unsound?
TS treats arrays and most generics as covariant for convenience; pushing a Cat into the Animal-typed array corrupts the Dog array; function parameters are checked contravariantly under strictFunctionTypes.
Covariance means `Box<Dog>` fits where `Box<Animal>` is expected. For readonly data that's safe, but a mutable array lets me push an Animal that isn't a Dog, so TypeScript accepts unsound code here by design. Function parameters go the other way: a handler accepting Animal can replace one accepting Dog, which strictFunctionTypes enforces for function types but not for methods. Knowing this explains many "why does this compile" moments.
Массивы и большинство дженериков ковариантны ради удобства — для мутабельных это небезопасно. Параметры функций контравариантны при strictFunctionTypes (кроме методов).

`satisfies` vs type annotation vs `as const` — when do you use each?
Annotation widens to the declared type; `satisfies` checks against a type but keeps the narrow inferred type; `as const` makes literals readonly and narrow.
If I annotate a config as `Record<string, Route>`, I lose the specific keys when I use it later. With `satisfies Record<string, Route>` the object is validated but keeps its literal keys, so `config.home` is still known. `as const` freezes literals so `'GET'` stays `'GET'` and arrays become readonly tuples. In practice `as const satisfies T` is the pattern for typed constant tables.
Аннотация расширяет тип; satisfies проверяет, но сохраняет точный вывод; as const сужает литералы. Для таблиц констант — as const satisfies T.

How do you make a switch over a union exhaustive, and why does `never` help?
In the default branch assign the value to `never`; when a new union member appears the assignment fails at compile time.
I write a helper like `assertNever(x: never)` and call it in the default case. After all cases are handled, the narrowed type is never, so it compiles. When someone adds a new variant to the discriminated union, the remaining type is no longer never and the build breaks exactly where the handling is missing. It's the cheapest safety net for reducers and status rendering.
В default присваиваю значение типу never (assertNever). Новый вариант union ломает компиляцию ровно там, где не обработан.

Enums vs union of string literals vs `as const` objects?
Prefer unions or `as const` objects: zero runtime, tree-shakable, work with isolatedModules; numeric enums are unsafe and `const enum` breaks across module boundaries.
A string literal union is just a type and costs nothing at runtime. When I also need the values at runtime, an `as const` object plus `typeof Obj[keyof typeof Obj]` gives both. TypeScript enums generate objects, numeric ones accept any number, and `const enum` can't be inlined across package or Babel/esbuild boundaries, which is why many codebases ban them.
Предпочитаю union литералов или as const объект: ноль рантайма, tree shaking. Числовые enum небезопасны, const enum ломается на границах модулей и с esbuild.

Which strict flags matter most, and what does `noUncheckedIndexedAccess` change?
strict as a baseline; plus noUncheckedIndexedAccess makes `arr[i]` and `obj[key]` return `T | undefined`, exactUseOptionalPropertyTypes separates missing from undefined, and verbatimModuleSyntax fixes type-only imports.
`strict` turns on null checks, implicit any detection, strict function types and bind/call/apply checks. noUncheckedIndexedAccess forces me to handle a missing element, which catches real bugs in loops and lookups at the cost of some noise. exactOptionalPropertyTypes distinguishes `{ a?: T }` from `{ a: T | undefined }`. verbatimModuleSyntax requires `import type`, so bundlers can drop type imports without a full type check.
strict — база; noUncheckedIndexedAccess делает индекс T | undefined; exactOptionalPropertyTypes отличает отсутствие от undefined; verbatimModuleSyntax требует import type.

How do you type a generic React component, and what's the catch with forwardRef?
Declare the generic on the function, `function Table<T>(props: TableProps<T>)`; forwardRef erases generics unless you cast or use React 19 where ref is a plain prop.
A generic component is a generic function, and TypeScript infers T from the props at the call site, so `<Table rows={users} />` types the render callbacks. forwardRef returns a non-generic component type, so the usual workaround was a cast or a module augmentation. In React 19 ref is a regular prop on function components, which removes the problem. For polymorphic `as` components I use a ComponentPropsWithoutRef pattern.
Дженерик-компонент — дженерик-функция, T выводится из пропсов. forwardRef теряет дженерик (нужен каст); в React 19 ref — обычный проп.

Where does TypeScript's type safety end at runtime, and what do you do about it?
Types vanish at compile time; data from the network, storage, URL params and `JSON.parse` is untyped, so validate at the boundary with zod/valibot and infer types from the schema.
Everything crossing a boundary is `unknown` in reality: API responses, localStorage, query strings, postMessage. A cast makes the compiler happy and hides the bug. I define a schema once with zod or valibot, parse at the boundary, and use `z.infer` so the type and the validation can't drift apart. In forms the same schema drives validation messages.
Типы исчезают в рантайме; сеть, storage, URL, JSON.parse — unknown. Валидирую на границе через zod/valibot и вывожу тип из схемы.

## React · Rendering internals

Walk through a React update: what happens between setState and the screen changing?
Schedule an update with a lane → render phase builds a work-in-progress Fiber tree (interruptible) → commit phase applies DOM mutations synchronously → layout effects → paint → passive effects.
Calling setState enqueues an update on the fiber with a priority lane and schedules work. In the render phase React calls components, diffs against the current tree and builds an effect list; with concurrent features this phase can pause and resume. The commit phase is synchronous: it applies DOM mutations, runs useLayoutEffect and ref callbacks, then the browser paints, and useEffect callbacks run afterwards. Understanding the two phases explains why render must be pure and why layout effects block paint.
setState → апдейт с приоритетом → render-фаза строит новое Fiber-дерево (прерываемо) → commit синхронно меняет DOM → layout-эффекты → paint → useEffect.

What problem does concurrent rendering solve, and what are lanes?
It lets React interrupt a low-priority render to handle urgent input; lanes are a bitmask of priorities so React can batch and reorder updates without the UI freezing on big renders.
Before concurrent rendering a large tree update blocked the main thread until done. Now React can yield to the browser every few milliseconds, check for higher-priority work like typing, and resume or restart. Lanes encode priority: sync input, default, transitions, idle. useTransition marks an update as low priority so a heavy filtered list doesn't delay the keystroke that caused it. The constraint is that render must be pure, because it may run more than once or be thrown away.
Конкурентный рендер прерывает тяжёлые обновления ради срочного ввода. Lanes — битовая маска приоритетов. useTransition помечает обновление как неприоритетное; рендер должен быть чистым.

useTransition vs useDeferredValue vs debouncing — when each?
useTransition for updates you trigger (set state without blocking input); useDeferredValue for a value you receive and want a lagging copy of; debounce when you want fewer requests, not just smoother rendering.
With useTransition I wrap the state update myself and get isPending for a spinner, so the input stays responsive while the expensive list renders in the background. useDeferredValue is for when I don't own the setter: I take a prop and React gives me a version that updates when it has time. Both only help with rendering cost. If the cost is network calls, I still need debouncing or request cancellation, and often both techniques together.
useTransition — когда я сам вызываю setState; useDeferredValue — для входящего значения. Оба про рендер; сетевые запросы всё равно требуют debounce и отмены.

Why does React double-invoke components and effects in StrictMode, and what does it catch?
To surface impure renders and non-idempotent effects before concurrent rendering or Fast Refresh breaks them; effects mount-unmount-mount so missing cleanups show up immediately.
In development StrictMode calls each component function twice and runs every effect's setup, cleanup and setup again. Rendering twice exposes side effects in render, like mutating a ref or calling an API. The effect double run exposes subscriptions and timers without cleanup, which would also break when React preserves state during Fast Refresh or future reusable state. It's annoying with analytics calls, but the fix is to make effects idempotent, not to remove StrictMode.
StrictMode дважды вызывает рендер и эффекты (setup→cleanup→setup), чтобы вскрыть нечистый рендер и эффекты без cleanup до того, как они сломаются в конкурентном режиме.

How does Suspense actually work under the hood?
A component throws a promise (or uses `use()`); the nearest Suspense boundary catches it, renders the fallback, and re-renders the subtree when the promise settles; data libraries cache so the second render reads synchronously.
Suspense is built on throwing: when data isn't ready, the component throws a thenable, React unwinds to the nearest boundary, shows the fallback and attaches a listener. When the promise resolves React retries the render, and the data source must return the result synchronously from a cache, otherwise it suspends forever. That's why raw fetch in a component doesn't work and why TanStack Query, Relay, or the React 19 `use` hook with a stable promise are needed. In concurrent mode boundaries can also hold back already-visible content via transitions.
Компонент бросает промис, ближайший Suspense ловит, показывает fallback и перерисовывает после resolve; источник данных должен кэшировать, иначе бесконечный suspend.

How does React decide whether to reuse or recreate a component instance during reconciliation?
Same type at the same position in the same parent, and the same key when in a list; a different type or key unmounts the subtree and its state.
Reconciliation is O(n) because it compares siblings by position and type instead of doing a full tree diff. If the element type changes, React tears the subtree down. If a key changes, the old instance unmounts and a fresh one mounts, which I exploit deliberately: changing `key` on a form resets it. Defining a component inside another component creates a new type every render, so its state resets, a classic bug.
Переиспользует при том же типе и позиции (и key в списке); иначе размонтирует вместе со стейтом. Смена key сбрасывает форму; компонент внутри компонента — новый тип каждый рендер.

What is tearing, and how does useSyncExternalStore prevent it?
Tearing is when one render shows two different versions of an external store because the render was interrupted; useSyncExternalStore forces a synchronous re-render if the store changed during rendering.
With concurrent rendering a long render can be paused, the store may change meanwhile, and components later in the tree read the newer value, so the UI is inconsistent for one frame. useSyncExternalStore subscribes to the store, snapshots it, and if the snapshot changed during render React falls back to a synchronous re-render. It's what Redux, Zustand and router libraries use under the hood, and it supports getServerSnapshot for SSR.
Tearing — в одном рендере две версии внешнего стора из-за прерывания. useSyncExternalStore сравнивает снимок и при изменении форсирует синхронный рендер; его используют Redux, Zustand.

Why does a portal's click bubble to a React parent that isn't its DOM ancestor?
React synthetic events propagate through the React tree, not the DOM tree; portals keep their position in the React tree, so handlers on ancestors still fire.
React attaches one native listener per event type at the root and dispatches synthetic events by walking its own fiber tree. A modal rendered via createPortal into document.body is still a child of its React parent, so onClick on that parent sees the modal's clicks. This is convenient for context and state, but it means click-outside logic must check the DOM with `contains` or use a real DOM listener instead of relying on React propagation.
Синтетические события всплывают по дереву React, а не DOM; портал остаётся ребёнком в React, поэтому родитель получает клики. Для click-outside нужна DOM-проверка.

Automatic batching — what changed in React 18 and what does flushSync do?
React 18 batches all state updates in the same tick, including promises, timeouts and native handlers; flushSync forces a synchronous commit for cases like measuring DOM right after an update.
React 17 batched updates only inside React event handlers, so two setState calls in a setTimeout caused two renders. With createRoot every update in the same microtask is batched. If I need the DOM updated immediately, for example to scroll to a newly added item, I wrap the setState in flushSync, accepting the performance cost. Reading state right after setState still gives the old value, batching or not.
React 18 батчит все обновления в одном тике (и в промисах, таймерах). flushSync форсирует синхронный коммит, например для измерения DOM после обновления.

## React · Hooks & patterns

Why do effects capture stale props, and how do you read the latest value without re-subscribing?
Closures capture the render's values; keep a ref updated with the latest callback or use useEffectEvent so the subscription effect has an empty dependency array but calls fresh logic.
An effect's callback closes over the props and state of the render that created it. If I subscribe once with `[]` and call `onMessage` inside, I call the first render's version forever. Adding the callback to deps re-subscribes on every render, which may be expensive or lose events. The pattern is a `latestRef` that an effect updates every render, or React's useEffectEvent, which gives a stable function that always sees current values and isn't a dependency.
Эффект замыкает значения своего рендера. Чтобы подписка жила с [] и видела свежий колбэк — ref с последним значением или useEffectEvent.

Callback refs vs useRef, and when do you need useImperativeHandle?
A callback ref runs when the node attaches or detaches, so it's right for measuring or observing; useRef is for stable storage; useImperativeHandle exposes a minimal imperative API from a child, like `focus()` or `scrollToRow()`.
useRef gives me a mutable box that survives renders but doesn't notify on change. A callback ref is called with the node on mount and null on unmount, so I can attach a ResizeObserver exactly when the element exists, even if it renders conditionally. useImperativeHandle lets a reusable component expose a small controlled surface to parents instead of leaking the DOM node. I keep it rare: data should flow through props, not imperative handles.
Callback ref срабатывает при появлении/удалении узла — для измерений и observers. useRef — хранилище. useImperativeHandle — минимальный императивный API (focus, scrollTo), редко.

Compound components, render props, HOCs and hooks — which problem does each pattern solve today?
Hooks share logic; compound components share implicit state across a flexible markup (`<Select><Select.Option/>`); render props still shine for inversion of rendering (virtualizers); HOCs are mostly legacy except for cross-cutting wrappers.
Hooks replaced most HOCs and render props for logic reuse because they compose without wrapper hell. Compound components use context to let consumers arrange parts freely while the parent owns the state, which is how Radix and Headless UI are built. Render props remain the cleanest way to hand rendering control to the consumer, like a virtual list asking how to render a row. I still see HOCs for things like `withAuth` at route level.
Хуки — переиспользование логики; compound components — общий стейт при свободной разметке (Radix); render props — отдать рендер потребителю (виртуализация); HOC — почти легаси.

What is derived state, and why is syncing props to state with useEffect an anti-pattern?
State that can be computed from other state or props should be computed during render, not copied; copying creates a stale frame and double renders; reset with `key` or compute on the fly.
If filteredItems can be computed from items and query, storing it in state means an extra render where it's out of date and a dependency array to maintain. I compute it inline, with useMemo if it's expensive. When a parent prop should reset local state, I change the component's key instead of writing an effect. The only legitimate "sync" is to an external system, which is what effects are for.
Производное состояние считается в рендере (useMemo при необходимости), а не копируется через useEffect — это лишний рендер и устаревший кадр. Сброс — через key.

When does React.memo not help, and how do you make it work?
It fails when props include new objects, arrays, inline callbacks or children elements every render; fix with useMemo/useCallback upstream, primitive props, or lifting the heavy part so it doesn't re-render at all.
memo does a shallow comparison, so any prop that is a fresh reference defeats it: `style={{}}`, `onClick={() => …}`, `items.filter(…)`, or JSX children. I either stabilize those references, pass primitives, or restructure: move state down to the component that needs it, or pass the expensive subtree as children so it's created by a parent that doesn't re-render. Measuring with the Profiler comes before adding memo everywhere.
memo ломается от новых ссылок в пропсах (объекты, inline-колбэки, children). Стабилизировать ссылки, передавать примитивы, или переставить стейт/children так, чтобы тяжёлое не рендерилось.

What does the React Compiler do, and what should you stop doing when it's on?
It auto-memoizes components and hooks by analyzing data flow, so manual useMemo/useCallback/memo become mostly unnecessary; it requires rules-of-react-compliant code (purity, no mutation of props/state).
The compiler rewrites components so values and callbacks are memoized based on their actual inputs, like fine-grained automatic useMemo. It can only do that safely for code that follows the rules: no mutation of props or state, no side effects in render, hooks called unconditionally. The ESLint plugin flags violations and the compiler skips those components. In practice I remove most manual memoization and keep my code pure.
Компилятор сам мемоизирует компоненты и хуки по потоку данных; ручные useMemo/useCallback почти не нужны. Требует чистого кода без мутаций; нарушители пропускаются.

How do you design state for a complex form: controlled, uncontrolled, or a form library?
Uncontrolled inputs with a form library (react-hook-form) scale best: no re-render per keystroke, schema validation with zod, controlled only for custom components.
Controlled inputs re-render on every keystroke, which is fine for a few fields and painful for a 50-field form. react-hook-form registers uncontrolled inputs through refs, subscribes to only the fields you watch, and plugs into zod for validation and types. For custom components like a date picker I use its Controller wrapper. The resulting state shape matches the schema, which also matches the API payload.
Для больших форм — неконтролируемые инпуты через react-hook-form + zod: нет рендера на каждый символ, типы из схемы; Controller — для кастомных компонентов.

How do you prevent context re-rendering the whole app, and when do you switch to a store?
Split contexts by change frequency, memoize the provider value, put stable setters in a separate context; when many components need slices of fast-changing state, move it to a store with selectors.
Every consumer re-renders when the context value changes, and the value is usually a fresh object. I separate "rarely changes" (theme, user) from "changes often" (cursor, draft), memoize the value, and give dispatch its own context so writers don't re-render readers. Context has no selector mechanism, so once I need `state.cart.count` without re-rendering on `state.filters`, I use Zustand or Redux where selectors subscribe to slices.
Разделять контексты по частоте изменений, мемоизировать value, setters в отдельный контекст. Нет селекторов — при частых срезах переходить на Zustand/Redux.

## React · Data & state

Server state vs client state — why treat them differently?
Server state is shared, async, can be stale and is owned by the backend; client state is local and synchronous. Use a query cache for the first, plain state or a small store for the second.
Data from an API has a lifecycle: loading, error, freshness, refetching, invalidation, pagination. Modelling that by hand in Redux produces thousands of lines of boilerplate. A query cache like TanStack Query or RTK Query handles it with keys, staleTime, retries and background refetch. True client state — open modal, selected tab, unsaved form — is small, so useState, URL params or a tiny store cover it. Mixing them is the most common architecture smell I see.
Серверное состояние — общее, асинхронное, устаревает; его ведёт query-кэш (TanStack/RTK Query). Клиентское — модалки, вкладки, формы — useState, URL, маленький стор.

How do you implement optimistic updates safely?
Cancel in-flight queries, snapshot the cache, write the expected result, send the mutation, roll back on error and invalidate on settle so the server truth wins.
In TanStack Query the pattern is onMutate: cancel outgoing refetches for the key, save the previous data, set the optimistic data; onError restores the snapshot and shows a toast; onSettled invalidates so the real response reconciles any difference. I only do this for operations with a high success rate and obvious UI, like toggling a like, and never for payments. Idempotency keys make retries of the same mutation safe.
onMutate: отменить refetch, снимок кэша, записать ожидаемое; onError — откат; onSettled — invalidate. Только для надёжных действий, не для платежей; idempotency key.

How do you avoid request waterfalls and race conditions in data fetching?
Fetch in parallel (Promise.all, parallel queries, prefetch on hover or in loaders), hoist fetching to route level, and ignore stale responses via abort or request IDs.
A waterfall appears when a child fetches only after its parent's data arrives; the fix is to start requests together, in a route loader or a parent that passes promises down with Suspense. For race conditions where an old response overwrites a new one, I abort the previous request in the effect cleanup or compare a request counter before setting state. Query libraries do both: they dedupe by key and keep only the latest result.
Водопады — фетчить параллельно и на уровне роута; гонки — abort предыдущего запроса в cleanup или сравнение id запроса. Query-библиотеки делают это по ключу.

Cache invalidation strategy: when do you refetch, invalidate or update the cache manually?
Invalidate by key prefix after mutations that affect lists; update the cache directly when the mutation returns the entity; use staleTime for read-mostly data and refetch on focus for collaborative data.
I start from the data's nature. Reference data gets a long staleTime and rarely refetches. Lists get invalidated after create or delete so pagination stays correct. For an edit I write the returned entity into the detail cache and patch the list item to avoid a flash. Refetch on window focus is on for dashboards others edit and off for forms. The goal is that the user never sees data older than they can tolerate, without redundant traffic.
Инвалидация по префиксу ключа после мутаций списков; прямое обновление кэша, когда мутация возвращает сущность; staleTime для справочников; refetch on focus для совместных данных.

How does Zustand avoid re-renders, and how is that different from Redux?
Store lives outside React; components subscribe with selectors and re-render only when the selected slice changes by reference; Redux does the same via useSelector but adds reducers, actions and middleware structure.
Zustand's store is a plain closure with a subscribe mechanism; `useStore(s => s.count)` compares the selected value and skips renders when unchanged. There's no provider, no action types, and slices can be composed. Redux Toolkit gives the same selector-based subscription but with immutable reducers through Immer, serializable actions, devtools time travel and middleware like listeners and RTK Query. I pick Zustand for app UI state and RTK when the team needs strict structure or already has it.
Zustand: стор вне React, подписка селектором, рендер только при смене среза. Redux — то же через useSelector плюс редьюсеры, действия, middleware, devtools.

What belongs in the URL, and how do you keep URL state in sync?
Anything the user may share, bookmark or restore: filters, pagination, selected item, tab; parse with a schema, update via the router with replace for high-frequency changes.
If a user refreshes and loses their filters, that's a bug. I keep filters, sort, page, selected entity and open tab in search params, parse them through a zod schema with defaults, and write back through the router. Typing in a search box uses `replace` and a debounce so history doesn't fill up. The URL then becomes the single source of truth and the state is shareable and testable.
В URL — фильтры, пагинация, выбранный элемент, вкладка; парсить схемой с дефолтами, писать через роутер, replace + debounce для частых изменений.

Infinite scroll with cursor pagination — how do you build it correctly?
useInfiniteQuery with a cursor from the server, an IntersectionObserver sentinel, virtualization for long lists, and stable keys; handle new items at the top separately from paging at the bottom.
The server returns items plus a nextCursor, which beats offsets when data changes underneath. A sentinel element at the end triggers fetchNextPage when it enters the viewport, with a hasNextPage guard to avoid double fetches. For thousands of rows I virtualize so the DOM stays small. Scroll restoration and "new posts" at the top are separate flows, because prepending shifts positions and must adjust scrollTop.
useInfiniteQuery с курсором, sentinel через IntersectionObserver, виртуализация, стабильные ключи; новые элементы сверху — отдельный поток с коррекцией scrollTop.

## Next.js & SSR

Where exactly is the server/client boundary in React Server Components, and what can cross it?
A file with 'use client' starts a client subtree; server components can render client components and pass serializable props, including other server-rendered elements as children, but not functions except server actions.
Everything in the App Router is a server component by default, so it can read the database and never ships to the client. `'use client'` marks the entry point to an interactive subtree. Props that cross must be serializable: no functions, class instances or Dates without conversion, but JSX from the server can be passed as children. A client component can't import a server component, only receive it. Server actions are the exception: functions that become RPC endpoints.
'use client' начинает клиентское поддерево; пропсы через границу — только сериализуемые (JSX как children можно, функции нет), кроме server actions.

Explain Next.js caching layers and how to invalidate them.
Request memoization within one render, the Data Cache for fetch across requests, the Full Route Cache for static output, and the Router Cache on the client; invalidate with revalidatePath, revalidateTag or `cache: 'no-store'`.
Within a single request identical fetches are deduplicated. Across requests the Data Cache stores fetch results until their revalidate time or until I call revalidateTag from a server action or webhook. Pages whose data is all cacheable become static HTML in the Full Route Cache. The client Router Cache keeps visited segments for back navigation. Debugging stale data is about finding which of these four layers served it, and Next 15 made fetch uncached by default to reduce surprises.
Четыре слоя: мемоизация в запросе, Data Cache между запросами, Full Route Cache для статики, Router Cache в браузере. Инвалидация — revalidatePath/Tag, no-store.

What causes hydration mismatches, and how do you fix them properly?
Rendering different output on server and client: Date.now, random, locale, window checks, browser extensions, or invalid HTML nesting; fix by moving browser-only logic to effects, suppressHydrationWarning for timestamps, or dynamic import with ssr:false.
Hydration attaches React to server HTML and expects an identical tree. Anything that differs breaks it: time-dependent text, `typeof window` branches that render differently, user locale formatting, or a `<div>` inside a `<p>` that the browser restructured. The fix is to render a neutral placeholder on the server and update in useEffect, use a `mounted` flag for browser-only widgets, and keep timezone-dependent formatting consistent via a shared locale. Suppressing warnings is a last resort for a single text node.
Сервер и клиент дали разное: Date.now, window, локаль, расширения, невалидная вложенность. Лечить переносом в useEffect, флагом mounted, dynamic ssr:false; suppress — крайняя мера.

Streaming SSR with Suspense — what does it change for the user and for the architecture?
The shell is sent immediately and slow parts stream in as they resolve, improving TTFB and LCP; it requires the slow data to be isolated behind boundaries and the page to be designed in independent chunks.
Instead of waiting for the slowest query before sending anything, the server flushes the layout and fallbacks, keeps the connection open, and streams HTML chunks plus inline scripts that swap them in. The user sees content earlier and can interact once hydrated selectively. Architecturally I wrap each independent data region in its own Suspense boundary and make sure fallbacks have the right size to avoid layout shift.
Сервер сразу отдаёт оболочку с fallback-ами, медленные части достримливает. Лучше TTFB/LCP; нужно изолировать медленные данные в Suspense и держать размеры fallback.

Server actions: how do they work, and what are the security concerns?
They compile to POST endpoints with an action ID; the client sends serialized args; you must authenticate and authorize inside the action and validate inputs, because anyone can call the endpoint.
A function marked 'use server' is replaced on the client with a reference; calling it posts the arguments to a Next endpoint that runs the function on the server. It integrates with forms and useActionState for progressive enhancement. Security-wise it's a public API: I re-check the session, authorize the specific resource, validate with a schema, and never trust a hidden id from the form. Closures over server data are encrypted but still shouldn't carry secrets.
'use server' → POST-эндпоинт по id действия. Это публичный API: внутри проверять сессию и права, валидировать вход схемой, не доверять скрытым полям.

Middleware/edge runtime vs Node runtime — what can and can't you do at the edge?
Edge runs close to the user with Web APIs only: no Node modules, fs or long tasks; use it for auth redirects, A/B, geolocation and header rewriting, not database-heavy logic.
Edge functions start fast and run in many regions, which makes them ideal for cheap decisions before a request hits the app: checking a cookie, redirecting unauthenticated users, picking a locale. They run on a restricted runtime with fetch, Request, Response, crypto and no Node built-ins, with tight CPU limits. Anything that needs a DB driver, ORM or heavy computation stays in the Node runtime.
Edge — быстрый старт у пользователя, только Web API, без Node-модулей и долгих задач: редиректы, A/B, гео, заголовки. База и тяжёлое — в Node runtime.

## Browser & Networking

How does the browser build layers and composite, and why do transform and opacity animate smoothly?
Elements promoted to their own layer are rasterized once and moved by the GPU; transform and opacity only change compositing, skipping layout and paint, while top/left or width trigger reflow.
After paint the browser splits content into layers and composites them on the GPU. Changing transform or opacity on a layered element only updates the compositor, so the main thread stays free and 60 fps is easy. Changing geometry invalidates layout and paint for the affected subtree. `will-change` hints a layer ahead of time, but too many layers cost memory. DevTools' Layers panel and the rendering flags show what's being repainted.
Слои растеризуются и двигаются GPU; transform/opacity меняют только композицию, без layout и paint. will-change заранее создаёт слой, но слоёв не должно быть много.

preload, prefetch, preconnect, dns-prefetch, modulepreload — what does each do?
preload fetches a resource for the current page with high priority; prefetch is low priority for the next navigation; preconnect opens the TCP+TLS connection early; modulepreload preloads ES modules with their dependencies.
preload tells the browser about something it would discover late, like a font or a hero image, and must be used or it wastes bandwidth. prefetch is a hint for the next page, done when idle. preconnect pays the handshake cost for a third-party origin ahead of time, and dns-prefetch is the lighter version. modulepreload is preload for ESM that also parses and compiles. Priority Hints via `fetchpriority` tune the order further.
preload — критичный ресурс этой страницы; prefetch — для следующей, в простое; preconnect — рукопожатие заранее; modulepreload — для ESM с парсингом.

How do HTTP caching headers interact: Cache-Control, ETag, Last-Modified, immutable?
Cache-Control max-age decides freshness; after that the browser revalidates with If-None-Match (ETag) and gets 304 if unchanged; hashed assets use `max-age=31536000, immutable`, HTML uses `no-cache` to always revalidate.
A fresh response is served from cache without a request. When it expires, the browser sends conditional headers and the server answers 304 cheaply. For fingerprinted bundles I set a one-year max-age with immutable since the URL changes on every deploy. For HTML I use no-cache, which still caches but always revalidates, so deploys propagate immediately. stale-while-revalidate serves the old version while fetching the new one in the background.
max-age — свежесть; потом условный запрос по ETag → 304. Хэшированные бандлы — год + immutable; HTML — no-cache (всегда ревалидация); stale-while-revalidate для плавности.

Service workers: what do you use them for, and what is the typical cache strategy mix?
A programmable network proxy for offline, caching and push; precache the app shell, cache-first for hashed assets, stale-while-revalidate for images, network-first for API data.
A service worker intercepts fetches from its scope and can answer from a cache, the network, or both. With Workbox I precache the shell at install, serve static assets cache-first, use stale-while-revalidate for images, and network-first with a fallback for API calls. The hard parts are update flow — a new worker waits until all tabs close unless I skipWaiting and notify the user — and never caching authenticated HTML by accident.
Программируемый прокси: precache оболочки, cache-first для хэшированных ассетов, SWR для картинок, network-first для API. Сложное — обновление воркера и не кэшировать приватный HTML.

Explain the CORS preflight in detail: when does it happen and how do you avoid it?
A preflight OPTIONS is sent for non-simple requests: methods other than GET/POST/HEAD, custom headers, or Content-Type other than form types; the server answers with Access-Control-Allow-* and Max-Age caches it.
A simple request like GET or a form POST goes straight out and the browser only checks the response headers. Anything with `Authorization`, `Content-Type: application/json` or PUT/DELETE triggers OPTIONS first, which costs a round trip. The server must echo the origin, allowed methods and headers, and `Access-Control-Allow-Credentials` if cookies are involved, in which case a wildcard origin is forbidden. `Access-Control-Max-Age` caches the preflight, and a same-origin proxy or BFF avoids CORS entirely.
Preflight OPTIONS — для non-simple запросов (JSON, Authorization, PUT/DELETE). Сервер отвечает Allow-*; с credentials нельзя *. Max-Age кэширует; BFF убирает CORS вовсе.

Cookies: SameSite, Secure, HttpOnly, Domain, Path, partitioning — what matters for auth?
HttpOnly blocks JS access (XSS can't steal), Secure requires HTTPS, SameSite=Lax blocks most CSRF while allowing top-level navigation, Strict is safer but breaks links from emails; third-party cookies are being partitioned.
For a session cookie I set HttpOnly so a script injection can't read it, Secure, and SameSite=Lax or Strict. Lax still sends the cookie on top-level GET navigations, so a POST-based CSRF is blocked but a login link from email works. If the frontend and API are on different registrable domains, I need SameSite=None with Secure, which requires CORS with credentials and a CSRF token. Browsers now partition third-party cookies by top-level site, which affects embedded widgets.
HttpOnly — не читает JS; Secure — только HTTPS; SameSite Lax блокирует CSRF, но пускает переходы по ссылке; разные домены → None + Secure + CSRF-токен; сторонние куки партиционируются.

WebSockets vs Server-Sent Events vs long polling — how do you choose?
SSE for server→client streams over HTTP with auto-reconnect and HTTP/2 friendliness; WebSockets for bidirectional low-latency (chat, collaboration, games); long polling only as a fallback.
SSE is a plain HTTP response that stays open; it reconnects automatically with Last-Event-ID, passes through proxies and works with HTTP/2 multiplexing, perfect for notifications and streamed AI output. WebSockets upgrade to a full-duplex socket and are right when the client sends a lot too, but I own reconnection, heartbeats and backpressure. Long polling is the universal fallback behind restrictive infrastructure.
SSE — поток сервер→клиент по HTTP с автопереподключением (уведомления, стриминг). WebSocket — двунаправленно и быстро (чат, коллаборация), но реконнект и heartbeats на мне.

What are Intersection, Resize and Mutation Observers, and what do they replace?
Async, batched callbacks for visibility, size and DOM changes; they replace scroll and resize listeners with getBoundingClientRect polling, which forced layout on every event.
IntersectionObserver reports when an element crosses a threshold relative to a root, without reading layout on scroll, so lazy loading and infinite scroll become cheap. ResizeObserver reports content size changes per element, which is how container-aware components work. MutationObserver reports DOM changes in batches, useful for integrating with third-party widgets. All three fire asynchronously, so I avoid layout thrashing by design.
IntersectionObserver — видимость (lazy load, бесконечный скролл), ResizeObserver — размер элемента, MutationObserver — изменения DOM; все асинхронные, без layout на каждом событии.

What does HTTP/2 and HTTP/3 change for frontend bundling decisions?
Multiplexing removes the head-of-line penalty, so many small files are fine and domain sharding or sprites are counterproductive; HTTP/3 over QUIC improves lossy mobile networks; compression and fewer bytes still matter most.
Over HTTP/1.1 we concatenated files because browsers opened only six connections per host. HTTP/2 multiplexes streams over one connection, so splitting the bundle into cacheable chunks improves cache hit rates without a request penalty. HTTP/3 moves to QUIC over UDP, which avoids TCP head-of-line blocking on packet loss, a big win on mobile. Neither makes bytes free: parsing and executing JS is still the bottleneck.
HTTP/2 мультиплексирует — много мелких чанков выгодно для кэша; шардинг и спрайты не нужны. HTTP/3 на QUIC лучше на плохих сетях. Байты и парсинг JS всё равно главное.

## Performance

How do you diagnose a slow React page step by step?
Reproduce with throttling → Performance panel for long tasks → React Profiler for render counts and "why did this render" → check network waterfalls → fix the biggest item and re-measure.
I start by reproducing under CPU and network throttling on a real-ish device profile. The Performance panel shows whether time goes to scripting, layout or network, and flags long tasks over 50 ms. If it's rendering, the React Profiler shows which components rendered, how often and why, and I look for wide commits caused by state high in the tree. If it's network, I look for waterfalls and oversized payloads. I fix one thing, measure again, and keep the Lighthouse or Web Vitals number as the regression check.
Воспроизвести с троттлингом → Performance (long tasks, что ест время) → React Profiler (кто и почему рендерится) → сеть (водопады, размеры) → чинить самое крупное и перемерять.

What is INP, and what typically causes a bad score?
Interaction to Next Paint: the latency from a user input to the next frame, across the whole visit; long JS tasks on click, heavy React commits, synchronous layout reads and third-party scripts are the usual culprits.
INP replaced FID and measures the worst interaction, roughly the 98th percentile, over the whole page life. A bad INP usually means a click handler does too much synchronously, a state update re-renders a huge tree, or a layout read after a DOM write forces a reflow. Fixes are to yield to the browser with scheduler.yield or setTimeout, defer non-urgent work with startTransition, virtualize lists, and isolate third-party scripts in workers via Partytown.
INP — задержка от ввода до следующего кадра за весь визит. Причины: долгие обработчики, тяжёлые коммиты, синхронные чтения layout, сторонние скрипты. Лечить yield, startTransition, виртуализацией.

Code splitting strategy: what do you split and what do you keep in the main bundle?
Split by route and by heavy, rarely used features (editor, charts, maps); keep the shell and above-the-fold code together; prefetch likely routes on hover or idle; watch for too many tiny chunks.
Route-based splitting with React.lazy or the framework's loader is the baseline. Then I split large libraries that aren't needed immediately: a rich text editor, a charting lib, a PDF viewer. Vendor chunks for stable dependencies improve long-term caching. Over-splitting creates request chains and duplicated code, so I check the bundle analyzer and the network waterfall. Prefetching on hover or with `requestIdleCallback` hides the chunk latency.
Делить по роутам и тяжёлым редким фичам (редактор, графики, карты); оболочку держать вместе; vendor-чанк для кэша; префетч по hover/idle; не дробить слишком мелко.

How do you optimize images and fonts for Core Web Vitals?
Responsive srcset with modern formats (AVIF/WebP), explicit width/height to avoid CLS, lazy load below the fold but preload the LCP image; self-host fonts, preload the main one, use font-display: swap or optional and size-adjust fallbacks.
Images are usually the LCP element, so the hero gets `fetchpriority="high"` and preload, while everything below the fold gets `loading="lazy"`. srcset and sizes give each device the right resolution, and AVIF or WebP halves the bytes. Width and height attributes reserve space so there's no layout shift. For fonts I self-host woff2, preload the primary face, limit weights, and tune fallback metrics so text doesn't jump when the font arrives.
Hero — preload и fetchpriority high, остальное lazy; srcset/sizes, AVIF/WebP, width/height против CLS. Шрифты self-host woff2, preload, font-display и подгонка fallback-метрик.

When is memoization harmful, and how do you decide?
Every useMemo/useCallback costs memory and comparison work, and wrong deps cause bugs; memoize only when profiling shows an expensive computation or a memoized child that re-renders because of reference changes.
Memoization isn't free: React stores previous values, compares dependencies, and the code gets harder to read. For cheap computations it's a net loss. I reach for it when the Profiler shows a component re-rendering with real cost or when a stable reference is required by a memoized child or an effect dependency. With the React Compiler the calculus changes because memoization becomes automatic and correct.
Мемоизация стоит памяти и сравнений, ошибочные deps дают баги. Применять по профилю: дорогие вычисления или стабильная ссылка для memo-ребёнка. С React Compiler — автоматически.

How do you find and fix layout thrashing?
Alternating DOM reads (offsetHeight, getBoundingClientRect) and writes in a loop forces synchronous reflow each time; batch reads, then writes, or use requestAnimationFrame and CSS instead of JS measurement.
Reading a layout property after a style change forces the browser to compute layout immediately, and doing it inside a loop over 100 elements means 100 reflows. The Performance panel shows them as purple Layout blocks with a "forced reflow" warning. I restructure to read everything first, then write, or use FastDOM-style scheduling, ResizeObserver for size, and CSS for what can be expressed declaratively.
Чередование чтений (offsetHeight) и записей форсирует reflow на каждом шаге. Сначала все чтения, потом записи; rAF, ResizeObserver, CSS вместо измерений в JS.

Virtualization vs pagination vs windowing — trade-offs?
Virtualization renders only visible rows (TanStack Virtual) and keeps the DOM small, but complicates accessibility, find-in-page and variable heights; pagination is simpler and SEO-friendly; combine with infinite query for feeds.
With a few thousand rows the DOM itself is the bottleneck, so I render only what's in view plus an overscan buffer, using absolute positioning inside a sized container. The costs are measuring dynamic row heights, screen-reader semantics, Ctrl+F, and scroll restoration. For tables users scan, classic pagination is often better and cheaper. Feeds get infinite query plus virtualization once they grow.
Виртуализация держит DOM маленьким, но усложняет a11y, поиск по странице, переменную высоту. Пагинация проще и для SEO. Ленты — infinite query + виртуализация.

## CSS & Layout

What is a stacking context, what creates one, and how does it affect z-index?
A stacking context is an isolated layer group created by positioned elements with z-index, opacity < 1, transform, filter, isolation, will-change and others; z-index only competes within the same context.
z-index isn't global. An element with `position` plus a z-index, or any transform, opacity below one, filter, or `isolation: isolate` creates its own stacking context, and all its children are stacked inside it. So a child with z-index 9999 can't escape a parent whose context sits below a sibling's. When a dropdown is hidden behind a header I look up the ancestors for the context, and the robust fix is a portal to the body plus a documented z-index scale.
Контекст наложения создают position+z-index, transform, opacity<1, filter, isolation. z-index сравнивается только внутри контекста. Выпадашки — через портал и шкалу z-index.

Containing block and the three "position" questions: what is `top: 0` relative to, what does `height: 100%` resolve against, and why does `position: fixed` sometimes scroll?
Positioned elements resolve against the nearest positioned ancestor's padding box; percentages resolve against the containing block; a transform or filter on an ancestor turns a fixed element into an absolute one relative to that ancestor.
For absolute elements the containing block is the nearest ancestor with a position other than static, for static elements it's the nearest block container, and for fixed it's the viewport, unless an ancestor has transform, filter, perspective or contain, which creates a new containing block and breaks fixed positioning. Percentage heights need a definite height on the containing block, which is why `height: 100%` often does nothing until the chain is explicit.
Абсолют — от ближайшего позиционированного предка; проценты — от containing block; transform/filter на предке превращает fixed в absolute относительно него.

Container queries, cascade layers and :has — how do they change how you write CSS?
Container queries style by the component's own width, not the viewport; @layer makes specificity wars explicit by ordering layers; :has enables parent and sibling-aware selectors without JS.
Container queries let a card switch layout when its container is narrow, regardless of the viewport, which is what design systems always needed. Cascade layers order resets, framework, components and utilities so a utility class wins regardless of specificity, which is how Tailwind and design systems avoid `!important`. `:has()` lets me style a form field when its input is invalid, or a card that contains an image. All three are widely supported now.
Container queries — стиль по ширине контейнера, не окна; @layer упорядочивает слои без войны специфичности; :has — стили по потомкам/соседям без JS.

CSS custom properties vs preprocessor variables vs CSS-in-JS runtime — what is the modern setup?
Custom properties are live, inheritable and themeable at runtime; Sass variables compile away; runtime CSS-in-JS costs on every render and is being replaced by zero-runtime solutions (vanilla-extract, Panda, Tailwind) in RSC-era apps.
Design tokens live best as CSS custom properties: they cascade, can change per theme or per component and are readable in JS via getComputedStyle. Preprocessor variables are static, fine for math at build time. Runtime CSS-in-JS like styled-components or Emotion injects styles during render, which hurts performance and doesn't work in Server Components, so the ecosystem moved to compile-time approaches with the same ergonomics.
Токены — CSS-переменные (живые, тематизируемые). Sass — статика на сборке. Runtime CSS-in-JS тормозит и не работает в RSC; тренд — zero-runtime (vanilla-extract, Panda, Tailwind).

How do you build a performant, accessible animation in CSS or with the Web Animations API?
Animate transform and opacity, use will-change sparingly, respect prefers-reduced-motion, keep durations 150–300 ms for UI, and use View Transitions or WAAPI for orchestrated sequences.
Compositor-only properties keep animations at 60 fps even when the main thread is busy. I avoid animating layout properties and height; for expand/collapse I use grid-template-rows or measure once and animate transform. prefers-reduced-motion must disable or shorten motion for users who need it. The Web Animations API gives me promises and playback control, and the View Transitions API handles page or state transitions declaratively.
Только transform/opacity, will-change дозированно, prefers-reduced-motion обязательно, 150–300 мс. WAAPI — контроль и промисы, View Transitions — переходы между состояниями.

Logical properties, intrinsic sizing and modern layout primitives — what do you use for i18n and responsive design without media queries?
margin-inline, padding-block and inset handle RTL automatically; min(), max(), clamp() give fluid type and spacing; grid with auto-fit/minmax and flex-wrap make layouts adapt without breakpoints.
Logical properties replace left and right with start and end, so Arabic and Hebrew layouts flip for free. clamp() gives fluid typography between a min and max, and `grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr))` builds responsive card grids with one line. Aspect-ratio, gap, and `fit-content` reduce the need for wrapper divs. Media queries then only handle real layout changes, not every width.
Логические свойства (inline/block) дают RTL бесплатно; clamp() — плавная типографика; grid auto-fit/minmax и flex-wrap — адаптив без брейкпоинтов.

## Architecture & Design

How do you structure a large frontend codebase so it stays maintainable?
Organize by feature or domain, not by file type; enforce dependency direction (shared → entities → features → pages) with lint rules; public API per module via index files; co-locate tests and styles.
Folders like components/, hooks/, utils/ scale badly because every feature touches all of them. I group by feature with clear layers and allow imports only downward, enforced by eslint-plugin-boundaries or Feature-Sliced Design rules. Each slice exposes a small public API so refactoring inside is safe. Shared UI lives in a design system package. The structure makes ownership obvious and keeps bundle splitting aligned with features.
Структура по фичам/доменам, слои с направлением зависимостей (shared→entities→features→pages), линт на импорты, публичный API модуля через index, тесты рядом.

Micro-frontends: when are they justified, and how would you integrate them?
Only when independent teams need independent deploys and the organizational cost outweighs the technical cost; integrate via Module Federation or import maps, share the design system and auth, isolate state and styles.
Micro-frontends solve a people problem, not a technical one: several teams shipping on their own schedules. The price is duplicated dependencies, inconsistent UX, cross-app routing and performance. If I do it, I use Module Federation or native ESM import maps with a shell app, pin shared singletons like React and the design system, communicate through URL and a small event contract, and keep CSS scoped. A monorepo with independent packages is often the better compromise.
Оправданы, когда независимые команды нуждаются в независимых деплоях. Интеграция: Module Federation/import maps, общий дизайн-системa и auth, изолированные стейт и стили. Часто монорепо лучше.

How do you design the API layer of a frontend app?
A single typed client generated from the OpenAPI/GraphQL schema, interceptors for auth and errors, a query layer on top, and domain mappers so UI never depends on raw backend shapes.
I generate types and a client from the schema so contract drift is caught at build time. One place handles the base URL, auth header refresh, error normalization and tracing headers. On top sits TanStack Query with query key factories per entity. If backend shapes are awkward, a thin mapper converts them to frontend models, so a backend rename touches one file. Mock Service Worker uses the same contract for tests and local development.
Типизированный клиент из OpenAPI/GraphQL, перехватчики auth/ошибок/трейсинга, сверху query-слой с фабриками ключей, мапперы в фронтовые модели; MSW на том же контракте.

How do you handle errors and loading states consistently across an app?
Classify errors (network, validation, auth, unexpected), map each to a UI pattern, use error boundaries per region with retry, skeletons sized like content, and report unexpected errors with context.
I define an error model early: a 401 triggers re-auth, a 403 shows a permission screen, validation errors attach to fields, network errors offer retry, unknowns show a friendly fallback and go to monitoring. Error boundaries wrap independent regions so one widget failing doesn't blank the page. Loading uses skeletons with reserved dimensions to avoid layout shift, and I avoid spinner cascades by hoisting data to route loaders.
Классификация ошибок → свой UI для каждой (reauth, права, поля формы, retry, fallback). Boundaries по регионам, скелетоны с размерами, неожиданное — в мониторинг с контекстом.

How do you roll out risky UI changes safely?
Feature flags with gradual rollout and kill switch, canary deploys, Web Vitals and error-rate monitoring per release, and A/B experiments with a clear metric; keep flags short-lived.
A flag service decides per user or percentage, so I can ship dark and enable for internal users first. I watch error rate, INP and conversion split by the flag, and the kill switch doesn't need a deploy. Source maps are uploaded so monitoring points at real code. Flags must have an owner and a removal date, otherwise the codebase fills with dead branches.
Фича-флаги с постепенным раскатом и kill switch, канарейки, мониторинг ошибок и Web Vitals по релизу, A/B с метрикой; флаги короткоживущие.

Design system: how do you build components that are accessible, themeable and hard to misuse?
Headless primitives (Radix/React Aria) for behaviour and a11y, tokens via CSS variables, variants with a typed API (cva), composition over boolean prop explosions, visual regression tests and docs in Storybook.
I don't reimplement a dropdown's keyboard and ARIA logic; I use a headless library and style it. Tokens for color, spacing and typography are CSS variables so themes switch without re-rendering. Variants are typed so `size="xl"` fails at compile time. Instead of `isPrimary isLarge isIcon` I compose slots and children. Storybook with interaction tests and Chromatic snapshots catches regressions, and the docs double as the contract with designers.
Headless-примитивы для поведения и a11y, токены в CSS-переменных, типизированные варианты, композиция вместо кучи boolean-пропсов, Storybook + визуальные тесты.

Internationalization: what breaks when you add a second language late?
Hardcoded strings, string concatenation, plural rules, date/number formatting, text expansion in layouts, RTL, sorting and casing; use ICU messages, Intl APIs, logical CSS and extraction tooling from day one.
Late i18n is expensive because strings are everywhere and sentences are built by concatenation, which breaks word order in other languages. ICU MessageFormat handles plurals and gender, Intl.DateTimeFormat, NumberFormat and RelativeTimeFormat handle locale output, and Intl.Collator sorts correctly. Layouts must survive 30% longer German text and RTL mirroring via logical properties. Lazy-loading locale bundles keeps the main bundle small.
Ломаются конкатенация строк, множественное число, форматы дат/чисел, расширение текста, RTL, сортировка. ICU, Intl.*, логический CSS, выделение строк с первого дня.

## Security & Quality

Content Security Policy — how do you deploy it in a React app without breaking everything?
Start with Report-Only, use nonces or hashes for scripts instead of unsafe-inline, strict-dynamic for bundler-loaded chunks, restrict connect-src and frame-ancestors, then enforce.
A strict CSP blocks inline scripts, which kills most XSS payloads even if an injection happens. I generate a per-request nonce on the server, put it on my script tags, and use `'strict-dynamic'` so scripts loaded by trusted scripts are allowed. connect-src limits where fetch can send data, frame-ancestors replaces X-Frame-Options against clickjacking. Rolling out in report-only mode with a reporting endpoint shows what would break before users feel it.
Сначала Report-Only; nonce/hash вместо unsafe-inline, strict-dynamic для чанков; connect-src и frame-ancestors; потом enforce.

Where do you store access and refresh tokens on the frontend, and why?
Refresh token in an HttpOnly, Secure, SameSite cookie; access token in memory (not localStorage); or a BFF that keeps tokens server-side and gives the SPA a session cookie.
localStorage is readable by any injected script, so a stolen token is an account takeover. Keeping the short-lived access token in a JS variable limits the window, and the refresh token in an HttpOnly cookie means JS can't read it; the refresh endpoint needs CSRF protection then. The cleanest architecture is a backend-for-frontend: the browser only has a session cookie and the BFF holds the OAuth tokens and talks to APIs.
Refresh — в HttpOnly Secure SameSite cookie, access — в памяти, не в localStorage; лучше BFF: у браузера только сессионная кука, токены на сервере.

Supply chain security: how do you protect a frontend from a malicious npm package?
Lock files and `npm ci`, pin versions and review updates, audit and Socket/Snyk scanning, minimal dependencies, provenance and ignore-scripts, CSP and SRI for third-party scripts.
Most attacks arrive through transitive dependencies or a compromised maintainer. I commit the lock file and install with `npm ci` so CI gets exactly what I reviewed, run audits plus a behavior-based scanner that flags install scripts and network access, and update in batches with a changelog check. `--ignore-scripts` in CI blocks the most common payload. For CDN scripts I use Subresource Integrity and a CSP, and I keep the dependency count small in the first place.
Lock-файл и npm ci, аудит и сканеры, минимум зависимостей, ignore-scripts в CI, обзор обновлений; для CDN — SRI и CSP.

Clickjacking, open redirects and tabnabbing — what are they and how do you prevent them?
Clickjacking: your page framed invisibly, blocked by frame-ancestors; open redirect: a `?next=` URL to an attacker site, blocked by allowlisting relative paths; tabnabbing: `target=_blank` pages controlling the opener, fixed with rel=noopener (now default).
An attacker frames my app and tricks users into clicking, so I forbid framing with CSP frame-ancestors. A login flow that redirects to whatever is in `?returnTo` becomes a phishing tool, so I only accept same-origin relative paths. Links opened in a new tab used to get `window.opener`, letting the new page navigate mine; modern browsers imply noopener, but I still set rel explicitly for older ones.
Фрейминг — frame-ancestors; редирект по ?next — только относительные пути из allowlist; target=_blank — rel=noopener.

How do you make sanitization and rich text safe in React?
Never use dangerouslySetInnerHTML with untrusted HTML; sanitize with DOMPurify using an allowlist, prefer rendering a parsed AST to React elements, and keep URLs validated against javascript: schemes.
React escapes text by default, so XSS enters via dangerouslySetInnerHTML, `href="javascript:"`, or third-party widgets. For user-generated HTML I sanitize with DOMPurify on the client and ideally also on the server, with a strict allowlist and hooks to force rel and target on links. For markdown I parse to an AST and render components, which gives safety and control. Trusted Types and CSP add defence in depth.
Без dangerouslySetInnerHTML для чужого HTML; DOMPurify с allowlist (и на сервере), markdown — через AST в компоненты, проверка схем ссылок; плюс CSP и Trusted Types.

## Testing

What do you test at each level of the frontend testing trophy?
Static (TS, ESLint) catches typos; unit for pure logic and hooks; integration with Testing Library and MSW for components with real behaviour, the biggest layer; a few E2E flows with Playwright for the critical paths.
Types and lint are the cheapest layer and catch a surprising share of bugs. Unit tests cover reducers, utils and complex hooks. Most of my tests are integration: render a feature with a real store and router, mock the network with MSW, and assert on what the user sees. E2E runs the money paths — login, checkout, main flow — against a real build, because they're slow and flaky by nature. Snapshot tests of markup I avoid; they fail on every change and prove nothing.
Статика (TS, lint) → unit для чистой логики → интеграционные с Testing Library и MSW как основной слой → немного E2E на критичные пути. Снэпшоты разметки — нет.

How do you test a custom hook and a component that fetches data?
renderHook with a wrapper providing QueryClient; for components, MSW handlers return realistic data, assert with findBy and waitFor, and test loading, success and error branches; avoid mocking fetch directly.
For hooks I use renderHook and a wrapper with the providers it needs, then act on returned functions and assert the result. For data components I start an MSW server with handlers for the endpoints, render with a fresh QueryClient that has retries disabled, and use findByText to await the loaded state. Error paths come from a handler returning 500. This way the tests survive refactors from fetch to axios to a generated client.
renderHook с wrapper провайдеров; компоненты с данными — MSW с реалистичными ответами, свежий QueryClient без ретраев, findBy/waitFor, ветки loading/success/error.

Why are E2E tests flaky and how do you make them reliable?
Timing assumptions, shared test data, network variance and animations; fix with auto-waiting locators, isolated seeded data per test, network mocking or test APIs, disabled animations, retries only as a signal, and traces on failure.
Flakiness is almost always a hidden race: asserting before the UI settles, tests depending on each other's data, or third-party calls. Playwright's locators auto-wait, so I avoid fixed sleeps. Each test seeds its own user through an API or fixture and cleans up. I mock external services and freeze time where needed. Retries hide problems, so I track flaky tests and fix them. Traces and videos on failure make CI failures debuggable.
Флаки — скрытые гонки: ждать по локаторам, изолированные данные на тест, мок внешних сервисов, выключить анимации, ретраи только как сигнал, трейсы на падении.

How do you test accessibility, and what can't be automated?
axe in unit and E2E runs catches ~30–40% of issues (contrast, missing labels, roles); keyboard navigation, focus order, screen-reader announcements and meaningful alt text need manual testing with a real screen reader.
Automated checks via jest-axe or Playwright's axe integration catch structural problems and fail the build, which is cheap and worth it. But most real barriers are about flow: can I complete the form with Tab and Enter, does focus land in the modal and return after closing, does a live region announce the result. I test with keyboard only and VoiceOver or NVDA at least for critical flows, and I use Testing Library queries by role, which keeps components accessible as a side effect.
axe в unit и E2E ловит треть проблем автоматически; клавиатура, порядок фокуса, объявления скринридера — только руками. Запросы по role в тестах держат a11y.

## Scenarios & live coding

The app gets slower the longer the user keeps the tab open. How do you investigate?
Suspect a memory leak or growing state: watch memory in the Performance monitor, take heap snapshots over time, check for unremoved listeners, intervals, subscriptions, and caches or stores that never evict.
I reproduce by using the app for a while and watching the memory graph; if it stairs up without coming down after GC, it's a leak. Heap snapshots before and after a repeated action show which objects accumulate and who retains them. Common culprits in React are subscriptions without cleanup, a query cache with infinite gcTime, a Redux list that keeps every page, and detached DOM kept by closures in third-party widgets. Then I add a regression test or a memory budget in CI.
Похоже на утечку: график памяти, heap snapshots до/после повторяемого действия, retainers; подписки без cleanup, кэш без gcTime, стор, растущий бесконечно.

A search box sends a request per keystroke and sometimes shows results for an older query. Fix it properly.
Debounce input, cancel the previous request with AbortController or let the query library dedupe by key, ignore responses whose query doesn't match the current input, and show stale results with a pending indicator rather than flicker.
Three problems hide here: too many requests, responses arriving out of order, and UI flicker. Debouncing 200–300 ms cuts requests. Cancelling the previous request in the effect cleanup or using a query keyed by the term guarantees only the latest result is applied. useDeferredValue or keepPreviousData keeps old results visible while new ones load. I also handle the empty query and minimum length cases.
Debounce, отмена предыдущего запроса (AbortController или ключ запроса), игнорировать несовпадающие ответы, keepPreviousData/useDeferredValue против мигания.

Design a reusable Autocomplete component. What do you consider beyond the happy path?
Keyboard navigation and ARIA combobox pattern, debounced async loading with cancellation, controlled/uncontrolled value, virtualization for long lists, portal rendering, loading/empty/error states, and a generic item type.
I start from the WAI-ARIA combobox pattern: roles, aria-activedescendant, arrow keys, Escape and Enter. The API accepts an async loader with an AbortSignal and a debounce option, supports both controlled and uncontrolled value, and renders items through a render prop so it's generic over T. The list renders in a portal to escape overflow and stacking contexts, virtualizes when long, and exposes loading, empty and error states. Tests cover keyboard flows and race conditions.
ARIA combobox и клавиатура, асинхронная загрузка с debounce и отменой, controlled/uncontrolled, дженерик по T через render prop, портал, виртуализация, состояния loading/empty/error.

Design a dashboard that shows live data for thousands of users. What's your architecture?
Server pushes via SSE/WebSocket into a normalized store, batch updates per animation frame, virtualize tables and charts, back off when the tab is hidden, and reconcile with a periodic full fetch.
Streaming updates can arrive faster than React can render, so I buffer them and flush once per frame with a single state update. The store is normalized by id so a tick updates one row, and components subscribe via selectors. Tables and charts are virtualized or canvas-based. When document.visibilityState is hidden I pause rendering and let the buffer collapse. A periodic snapshot fetch heals any missed events, and the connection reconnects with backoff.
Push через SSE/WebSocket в нормализованный стор, батчить обновления по кадру, селекторы, виртуализация/canvas, пауза в скрытой вкладке, периодический полный снимок, reconnect с backoff.

Migrating a large class-component codebase to hooks and TypeScript — how do you plan it?
Incrementally: enable TS with allowJs and loose settings, convert leaf components first, codemods for mechanical parts, feature flags for risky screens, and tests before refactors; never a big-bang rewrite.
I keep the app shippable the whole time. TypeScript goes in with `allowJs` and `strict: false`, then I tighten flags per folder. Class components are converted when touched or by risk, starting at the leaves because they have fewer dependencies. Codemods handle imports and simple patterns, and Testing Library tests written before conversion guard behaviour. I track progress with a dashboard so the migration has visible momentum and an end date.
Инкрементально: TS с allowJs и мягкими флагами, ужесточать по папкам; конвертировать с листовых компонентов, кодмоды, тесты до рефакторинга, без big-bang.

How do you approach a live-coding task in an interview?
Clarify requirements and edge cases, state assumptions, outline the approach and complexity, write a working version first, test with examples out loud, then refactor and discuss trade-offs and what you'd do in production.
I repeat the task in my own words and ask about inputs, scale and edge cases, then say the plan and its complexity before typing. I write the simplest correct version, run through two or three examples including an empty input, and only then clean up names and structure. Throughout I narrate what I'm doing and why, and I finish with what I'd add for production: tests, error handling, accessibility, performance.
Уточнить требования и крайние случаи, озвучить план и сложность, написать рабочую версию, прогнать примеры вслух, затем рефакторинг и trade-offs, что добавил бы в продакшене.

## Algorithms for live coding

Which data structure gives O(1) lookups in JS, and when do you pick Map over an object?
Map and Set are hash-based with O(1) average operations; prefer Map when keys aren't strings, order matters, you add and delete a lot, or the key set is user-controlled (no prototype issues).
Objects work as string-keyed hash maps, but keys get coerced to strings, iteration order has special rules for integer-like keys, and user-controlled keys risk `__proto__`. Map keeps any key type, remembers insertion order, has a size property and performs better under heavy insert and delete churn. Set is the go-to for deduplication and membership tests. Most two-pass interview solutions — two sum, anagram groups, counting — are one Map away.
Map/Set — O(1) в среднем; Map вместо объекта, когда ключи не строки, важен порядок, много вставок/удалений или ключи от пользователя (нет __proto__).

Two pointers and sliding window — when do you reach for them?
Sorted arrays and pair/substring problems: two pointers converge from both ends or move in one direction; a sliding window keeps a running state over a contiguous range to turn O(n²) into O(n).
If the input is sorted, two pointers find pairs with a target sum or merge sequences in linear time. For "longest substring without repeats" or "max sum of k consecutive", a window with a left and right index plus a Map of counts avoids recomputing the range each time. The tell is the phrase "contiguous" or "subarray"; then I think window before nested loops.
Два указателя — отсортированные массивы и пары; скользящее окно — непрерывные подстроки/подмассивы с состоянием, O(n²) → O(n).

How do you traverse a tree like the DOM, and what's the difference between BFS and DFS?
DFS goes deep first (recursion or an explicit stack) and suits path and subtree problems; BFS goes level by level with a queue and finds the shallowest match; both are O(n).
A recursive DFS mirrors how React renders a tree and is what I use for flattening, searching a subtree or computing depth. Deep trees can blow the call stack, so an explicit stack version is safer. BFS with a queue visits nearest nodes first, which answers "closest element with class X" or level-order rendering. For the DOM there's also TreeWalker, but on a whiteboard I write the loop.
DFS — вглубь (рекурсия или стек), для подзадач по поддереву; BFS — по уровням через очередь, ближайшее совпадение. Глубокие деревья — явный стек вместо рекурсии.

Explain memoization vs dynamic programming with a frontend-flavoured example.
Memoization caches results of pure function calls (top-down); DP builds a table from small subproblems (bottom-up); e.g. computing text layout breaks or edit distance for a fuzzy search.
Memoization is what useMemo and reselect do: cache by input and reuse. In algorithms it turns an exponential recursion like Fibonacci or edit distance into polynomial time. Dynamic programming reorders the same idea into iteration over a table, which avoids recursion depth and often reduces memory to a single row. Fuzzy matching in a command palette and diffing two lists are everyday places where this matters.
Мемоизация — кэш результатов сверху вниз; DP — таблица снизу вверх, без глубокой рекурсии. Примеры: fuzzy-поиск (edit distance), диффы списков.

How do you implement an LRU cache, and where would you use one in a frontend?
A Map plus its insertion order: on get, delete and re-insert the key to mark it recent; on set beyond capacity delete the first key; O(1) for both; used for memoizing expensive renders, images or API responses.
JavaScript's Map iterates in insertion order, so moving a key to the end is delete-then-set and the oldest is `map.keys().next().value`. That gives a clean O(1) LRU in about fifteen lines, which is a common live-coding question. In practice this is how I'd bound a client-side cache of search results, parsed documents or rendered thumbnails so memory doesn't grow forever.
Map хранит порядок вставки: get — удалить и вставить снова, set сверх лимита — удалить первый ключ, O(1). Для ограниченных кэшей результатов поиска, картинок.

What's the complexity of common array methods, and how do you avoid accidental O(n²) in React code?
includes, indexOf, find, splice and unshift are O(n); nested loops over lists, `array.find` inside `map`, and sorting inside render are the usual quadratic traps; precompute a Map or an index once.
Rendering a list where each row calls `users.find(u => u.id === row.userId)` is O(n·m) every render; a `Map` built once with useMemo makes it O(n). Sorting or filtering inside render without memo repeats O(n log n) work per keystroke. `unshift` and `splice` at the front are O(n), so building arrays by prepending in a loop is quadratic. I call out these complexities while coding so the interviewer sees I think about scale.
find внутри map, сортировка в рендере, unshift в цикле — скрытое O(n²). Строить Map/индекс один раз через useMemo и называть сложности вслух.
