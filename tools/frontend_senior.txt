## JavaScript · Engine & memory

How does V8 run JavaScript, and why should objects keep the same shape?
V8 first runs the code with an interpreter (Ignition). Hot code is compiled by TurboFan. The compiled code is fast only if objects keep the same fields in the same order.
V8 turns the code into bytecode and runs it. While it runs, it watches which types it sees. Code that runs often is compiled to fast machine code. This fast code expects objects to look the same every time: same fields, same order. If I add fields in a different order, or change a field from number to string, the fast code is thrown away. So I create objects in one place with all fields, and I do not use delete in hot code.
V8 сначала интерпретирует, горячий код компилирует. Быстрый код ждёт одинаковую форму объектов (те же поля, тот же порядок). Иначе деоптимизация.

How does garbage collection work in V8?
The heap has two parts. The young part is small and is cleaned often and fast. Objects that live long move to the old part, which is cleaned rarely, in small steps and in the background.
Most objects die very fast. So V8 keeps new objects in a small young space and cleans it often. This cleaning is cheap. Objects that survive two cleanings move to the old space. The old space is cleaned with mark and sweep. This is done in small steps and partly in background threads, so the page does not freeze. One important point: even without a leak, creating many objects very fast makes the GC work hard, and the user sees small freezes.
Молодое поколение чистится часто и дёшево, старое — редко, инкрементально и в фоне. Даже без утечек много аллокаций даёт фризы.

What are the common memory leaks in a single-page app, and how do you find them?
Listeners and timers that are never removed, closures that hold big data, DOM nodes that are removed from the page but still referenced, caches that only grow. Find them with heap snapshots.
The usual leaks are simple. An event listener or setInterval that nobody removes. A closure that keeps a big array alive. A DOM node that is removed from the page but still stored in a variable. A cache or a store that grows and never deletes anything. To find them, I open DevTools, take a heap snapshot, repeat the action several times, take another snapshot, and compare. I look at what grew and who holds it. The allocation timeline shows which code creates the objects.
Утечки: неснятые слушатели и таймеры, замыкания с большими данными, удалённые DOM-узлы в переменных, растущие кэши. Ищу сравнением heap snapshots.

WeakMap, WeakSet, WeakRef and FinalizationRegistry — when do you use them?
WeakMap keys do not keep objects alive. Use it to attach data to an object without a leak. WeakRef and FinalizationRegistry are only for optional caches, never for logic.
A normal Map keeps its keys alive forever. A WeakMap does not: when the key object is gone, the entry is gone too. So I use it to store extra data about an object, for example private data or a cache by object. A WeakRef is a reference that can become empty at any time. A FinalizationRegistry calls a function after an object is collected. We never know when that happens, so I use these two only for caches where losing data is fine.
WeakMap не удерживает ключи — для метаданных и кэшей по объекту. WeakRef и FinalizationRegistry непредсказуемы, только для необязательных кэшей.

structuredClone vs JSON.parse(JSON.stringify()) vs spread?
Spread copies only the top level. The JSON trick loses undefined, Dates, Maps and breaks on cycles. structuredClone makes a real deep copy but cannot copy functions or DOM nodes.
Spread is a shallow copy. Nested objects are still shared. The JSON trick is a deep copy but with problems: undefined is removed, a Date becomes a string, Map and Set become empty objects, and a circular reference throws. structuredClone is the right tool for a deep copy. It handles Dates, Maps, Sets and cycles. But it throws on functions and DOM nodes, and class instances become plain objects.
Spread — поверхностно; JSON теряет undefined, Date, Map, падает на циклах; structuredClone — настоящая глубокая копия, но без функций и DOM, классы становятся объектами.

What is the difference between the call stack, the heap and the task queues?
The stack holds the functions that run right now. The heap holds objects. The queues hold callbacks that wait for the event loop.
The call stack is the list of functions that are running now. If recursion goes too deep, the stack overflows. The heap is the memory where objects live; the garbage collector manages it, and a leak means the heap grows. The task queues hold callbacks, for example from setTimeout or promises. The event loop takes them one by one when the stack is empty. A long function on the stack blocks the loop, and the page freezes.
Стек — текущие функции (переполнение при глубокой рекурсии), куча — объекты (утечка = рост), очереди — колбэки для event loop (долгая задача = фриз).

## JavaScript · Async deep dive

In what order do microtasks, macrotasks, requestAnimationFrame and rendering run?
One macrotask runs. Then all microtasks run, including new ones. Then, if it is time for a frame, requestAnimationFrame callbacks run and the browser paints. The next macrotask waits for the next turn.
The event loop takes one macrotask, for example a click handler. After it, the loop runs every microtask, so all promise callbacks. If a microtask adds another microtask, it also runs now. This is why an endless promise chain freezes the page. Then, if the screen needs a new frame, the browser runs requestAnimationFrame callbacks, calculates layout and paints. setTimeout with zero delay is a new macrotask, so it runs after the paint may already have happened.
Макрозадача → все микрозадачи (и новые тоже) → при кадре rAF и рендер. Бесконечные микрозадачи блокируют отрисовку; setTimeout(0) — следующий оборот.

What does async/await become after compilation, and how much does await cost?
An async function becomes a state machine built on promises. Each await pauses the function. Waiting on a native promise costs one microtask. Code after await never runs synchronously.
An async function is split into steps. Each await is a point where the function stops and later continues from a promise callback. Since 2019, await on a native promise costs one microtask. Even `await 42` goes to the microtask queue. So the code after await always runs later, not right now. This matters for tests that check order, and for try/catch: inside a try block I must write `return await`, otherwise the catch does not see the error.
Async-функция — машина состояний на промисах; await стоит один microtask; код после await всегда позже; внутри try/catch нужен return await.

How do you cancel an async operation in JavaScript?
Promises cannot be cancelled. Use AbortController. Pass its signal to fetch and to your own functions, check it between steps, and call abort in the cleanup.
A promise has no cancel method. The standard tool is AbortController. I create a controller and pass controller.signal to fetch, to addEventListener and to my own async functions. Inside them I check signal.aborted between steps or stop when the abort event fires. In React I create the controller inside useEffect and call abort in the cleanup function. This also fixes the problem when an old request finishes after a new one. AbortSignal.timeout and AbortSignal.any help to combine a timeout with user cancel.
Промисы не отменяются. AbortController: signal в fetch и свои функции, проверка между шагами, abort в cleanup эффекта. AbortSignal.timeout/any для комбинаций.

What is an unhandled rejection, and how do you handle errors globally in the browser?
A promise was rejected and nobody added a catch in time. Listen to the unhandledrejection and error events, use error boundaries in React, and send errors to a monitoring service.
If a promise rejects and no catch is attached before the microtask queue is empty, the browser fires the unhandledrejection event. I listen to it and to window.onerror for normal errors. I send them to a service like Sentry with the user id and the app version, and I show a simple fallback. Render errors in React go to error boundaries. But errors in event handlers and in async code do not reach boundaries, so the global handlers are the safety net.
Промис отклонён без catch → unhandledrejection; плюс window.onerror и error boundaries, отправка в мониторинг. Ошибки в хендлерах и async до boundary не доходят.

Async iterators and generators — where are they useful on the frontend?
For data that comes over time: reading a stream, server-sent events, or pages of an API. for await gives you back-pressure and a simple way to stop.
An async generator is a function that gives values one by one, and each value can arrive later. I use it to read a fetch body as a stream, to consume server-sent events, or to walk through API pages. The consumer uses for await. It asks for the next value only when it is ready, so the producer does not run ahead. To stop, I just break out of the loop. The logic is also easy to test without React.
Асинхронные генераторы — данные со временем: стримы, SSE, страницы API. for await даёт back-pressure, остановка через break.

Web Workers — what would you move there, and how?
Heavy CPU work that does not touch the DOM: parsing big files, diffing, image processing. Talk to the worker with postMessage, send big buffers as Transferable so they are not copied.
A worker is a second thread. It cannot touch the DOM, but it can do heavy work while the page stays smooth. Good candidates are parsing a big JSON or CSV, building a search index, compressing or resizing images. The page and the worker talk with postMessage. For big data I transfer the ArrayBuffer instead of copying it. A library like Comlink makes worker calls look like normal async functions. A service worker is different: it is a network proxy, not a place for computations.
В воркер — тяжёлые вычисления без DOM. Общение через postMessage, ArrayBuffer передавать без копии, Comlink для удобства. Service worker — другое, это сетевой прокси.

How do you implement retry with exponential backoff correctly?
Retry only safe requests and only retryable errors (network, 429, 5xx). Wait longer after each try, add random jitter, set a maximum, respect Retry-After, and stop on abort.
First I check that the request is safe to repeat. A GET is safe. A POST is safe only if it has an idempotency key. Then I check the error: network errors, 429 and 5xx can be retried; 400 or 401 cannot. The delay grows, for example 1, 2, 4 seconds, with a random part so that many clients do not retry at the same moment. If the server sends a Retry-After header, I use that value. I stop after a few tries, and I also stop if the AbortSignal fires.
Ретраить только безопасные запросы и ретраибельные ошибки (сеть, 429, 5xx). Задержка растёт с джиттером, лимит попыток, Retry-After, стоп по signal, idempotency key для POST.

setTimeout, setInterval, requestAnimationFrame, requestIdleCallback — what is the difference?
setTimeout runs once after at least the given delay. setInterval repeats and can pile up. requestAnimationFrame runs before the next paint. requestIdleCallback runs when the browser has free time.
setTimeout gives a minimum delay, not an exact one, and background tabs slow it down. setInterval keeps firing even if the previous callback is still slow, so I usually use setTimeout that calls itself. requestAnimationFrame runs right before the browser paints and stops in hidden tabs. It is the right place for animations and for reading layout. requestIdleCallback runs when the browser has nothing else to do, so it is good for low-priority work like analytics, and it gives a deadline I must respect.
setTimeout — минимальная задержка; setInterval накапливается; rAF — перед кадром, для анимаций и измерений; rIC — в простое, для неприоритетного.

How does fetch streaming work, and when would you use it?
response.body is a ReadableStream. Read it chunk by chunk with a reader, decode with TextDecoder, and show the data as it arrives. Useful for AI text streams and big downloads.
Normally I call response.json() and wait for the whole body. With streaming I take response.body.getReader() and read small chunks as they come. I decode them with a TextDecoder in stream mode and show the text right away. This is how chat apps show AI answers word by word. It also lets me start rendering a big list before the download ends. The abort signal cancels the stream. When I split the text by lines, I must keep the last incomplete piece for the next chunk.
response.body — ReadableStream: читаю чанки, декодирую TextDecoder, показываю сразу (стриминг ответа ИИ, большие выгрузки); отмена через signal.

## JavaScript · Language internals

What is the iterable protocol, and why does spread work on a Map but not on a plain object?
An object is iterable if it has a Symbol.iterator method that returns an object with next(). Map, Set, arrays and strings have it. Plain objects do not.
for-of, array spread, Array.from and destructuring all use one protocol. They call the Symbol.iterator method and then call next() until done is true. Map, Set, arrays and strings have this method. A plain object does not, so `[...obj]` throws. But `{...obj}` works, because object spread does not use the protocol; it just copies own keys. I can make my own class iterable by adding a generator method named Symbol.iterator.
Итерируемое = есть Symbol.iterator, который возвращает объект с next(). Map/Set/массивы — да, объект — нет; поэтому [...obj] падает, а {...obj} работает через ключи.

What are Proxy and Reflect, and which libraries use them?
A Proxy wraps an object and lets you intercept reads, writes, deletes and other operations. Reflect gives the default behaviour. Vue 3, MobX, Immer and Valtio are built on Proxy.
A Proxy sits between the code and the object. When the code reads a field, the Proxy's get trap runs; when it writes, the set trap runs. Reflect.get and Reflect.set do the normal operation, so a trap can do its work and then call the default. Vue 3 uses the get trap to remember which component read a field, and the set trap to update that component. Immer uses a Proxy to record changes and then builds a new immutable object. The cost is speed in hot code, and a Proxy cannot be polyfilled.
Proxy перехватывает операции с объектом, Reflect делает стандартное действие. На этом стоят Vue 3, MobX, Immer. Минусы — скорость и нет полифила.

What are Symbols for, besides unique keys?
Well-known symbols connect your object to language features: Symbol.iterator, Symbol.asyncIterator, Symbol.toPrimitive, Symbol.hasInstance. Symbol.for gives a shared symbol by name.
A symbol is a unique key that JSON.stringify and Object.keys skip. The well-known symbols are hooks into the language. Symbol.iterator makes an object work with for-of. Symbol.toPrimitive controls what happens when the object is turned into a string or a number. Symbol.hasInstance customizes instanceof. Symbol.for('name') returns the same symbol everywhere, even across iframes. React uses it for the $$typeof field on elements, so that an element from JSON cannot be injected.
Символы — уникальные ключи, невидимые для JSON и keys; well-known символы — хуки языка (iterator, toPrimitive, hasInstance); Symbol.for — общий символ по имени.

How do ES modules differ from CommonJS at runtime?
ES modules are linked before the code runs, imports are live bindings, and loading is async. CommonJS runs require synchronously and copies the value. Mixing them gives "default is undefined" bugs.
With ES modules the browser or bundler first reads all import and export statements, builds the graph and links everything. Only then the code runs. An import is a live link: if the exported value changes, the importer sees the change. Top-level await is possible. CommonJS is different: require is a normal function call that runs the file right now and returns module.exports as it is at that moment. When tools mix the two, a CommonJS module shows up as an object with a default field, and that is where "default is undefined" comes from. Tree shaking needs the static ES module graph.
ESM — статическая линковка, живые привязки, асинхронно; CJS — синхронный require, копия значения. Смесь даёт default undefined; tree shaking работает только с ESM.

How do class fields, private fields and arrow methods work with this?
Class fields are created for each instance before the constructor body. #private fields are really private. An arrow function field keeps this, but each instance gets its own copy and a subclass cannot override it through the prototype.
Field initializers run for every new instance, in order, before the constructor body, and this is already set. A field with # is private: no code outside the class can read it, and `#x in obj` checks if an object has it. An arrow function as a field captures this, so I can pass it as a callback safely. The price: every instance holds its own function, and a subclass cannot override it on the prototype. Normal methods are shared through the prototype and lose this when passed as callbacks.
Поля создаются до тела конструктора; #private — настоящая приватность; стрелочное поле держит this, но копируется на каждый экземпляр и не переопределяется через прототип.

What is prototype pollution, and how do you protect against it?
An attacker sends JSON with a __proto__ key. A deep merge writes it to Object.prototype, and every object changes. Block the keys __proto__, constructor and prototype, use Map, and keep libraries updated.
Imagine a deep merge function that copies user JSON into a config object. If the JSON has a key "__proto__", the merge writes to Object.prototype. Now every object in the app has that field, for example isAdmin: true. To protect: the merge and the deep-set helpers must skip the keys __proto__, constructor and prototype. User data is better kept in a Map or in an object created with Object.create(null). And I keep libraries like lodash updated, because they had exactly this bug.
Deep merge чужого JSON с ключом __proto__ меняет Object.prototype. Защита: блокировать __proto__/constructor/prototype, Map или null-прототип, обновлять библиотеки.

Explain property descriptors, getters and setters, and Object.freeze.
Every property has flags: writable, enumerable, configurable, or a get/set pair. Object.freeze sets writable and configurable to false, but only on the top level. Getters make computed values look like fields.
Object.defineProperty lets me set the flags of a property. writable means it can change, enumerable means it shows up in loops and in spread, configurable means it can be deleted or changed again. A property can also be a pair of get and set functions. Object.freeze turns off writable and configurable for all own properties, but nested objects are not frozen, so a deep freeze needs recursion. Vue 2 and MobX used getters and setters to watch changes before Proxy existed. A non-enumerable property is a way to hide a helper field from JSON and spread.
Дескрипторы: writable/enumerable/configurable или get/set. freeze поверхностный. Геттеры дали реактивность до Proxy; non-enumerable скрывает поле от JSON и spread.

## TypeScript · Advanced types

Conditional types with infer — how do you get a function's return type or a promise's value?
`T extends (...a: any[]) => infer R ? R : never` gives the return type. `T extends Promise<infer U> ? U : T` unwraps a promise. A conditional type over a union is applied to each member.
infer declares a type variable inside the extends check, and TypeScript finds its value. This is how ReturnType, Parameters and Awaited are written. When the type parameter is a union, TypeScript applies the conditional type to each member separately, so Unwrap<A | B> becomes Unwrap<A> | Unwrap<B>. Usually this is what I want. If not, I wrap both sides in a tuple: `[T] extends [X]`.
infer — переменная типа внутри extends; так написаны ReturnType, Parameters, Awaited. Условный тип применяется к каждому члену union; обернуть в кортеж, чтобы выключить.

Mapped types and template literal types — give a practical example.
A mapped type goes over the keys of another type and can rename or filter them with `as`. With template literals you can build keys like onNameChange from name.
A mapped type is a loop over keys: `{ [K in keyof T]: ... }`. With the as clause I can change the key name or drop some keys. Template literal types build strings at the type level. Together they let me take a props type and produce an event handlers type, for example onNameChange for the field name. Another example is typed route params from a path like "/users/:id". The compiler then catches renames for free.
Mapped type — цикл по ключам, as переименовывает/фильтрует; шаблонные литералы строят имена: onNameChange из name, типизированные параметры роута из пути.

What is structural typing, and when does it cause problems?
Types are compared by their shape, not by their name. So a UserId and an OrderId, both strings, can be mixed by mistake. Branded types fix this.
In TypeScript, if two types have the same fields, they are compatible. This is flexible, but it has a downside: two different IDs that are both strings can be swapped and nothing complains. The fix is a branded type: `type UserId = string & { __brand: 'UserId' }` and a small function that creates it. Another surprise: extra properties are checked only when you write an object literal directly, not when you pass a variable.
Типы сравниваются по форме, не по имени: UserId и OrderId как string можно перепутать. Решение — брендированные типы; проверка лишних полей только для литералов.

Why can you pass Array<Dog> where Array<Animal> is expected, and why is that unsafe?
TypeScript treats arrays as covariant for convenience. But a mutable array lets you push a Cat into what is really a Dog array. Function parameters are checked the other way with strictFunctionTypes.
If Dog is an Animal, TypeScript also says Array<Dog> is an Array<Animal>. For reading this is fine. For writing it is not: through the Animal-typed reference I can push a Cat into the Dog array. TypeScript allows this on purpose, because the strict version would be very annoying. Function parameters work in the opposite direction: a function that accepts Animal can be used where a function that accepts Dog is expected. strictFunctionTypes enforces this for function types, but not for methods.
Массивы ковариантны ради удобства, для мутабельных это небезопасно. Параметры функций проверяются наоборот (strictFunctionTypes), но не для методов.

satisfies vs a type annotation vs as const — when do you use each?
A type annotation widens the value to the declared type. satisfies checks the value against a type but keeps the exact inferred type. as const makes literals readonly and exact.
If I write `const routes: Record<string, Route> = {...}`, TypeScript forgets the real keys, so routes.home is just a Route and may not exist. With `satisfies Record<string, Route>`, the object is checked, but its exact keys stay known. as const makes values exact: 'GET' stays the literal 'GET', arrays become readonly tuples. For tables of constants I use both together: `as const satisfies T`.
Аннотация расширяет тип; satisfies проверяет, но сохраняет точный вывод; as const сужает литералы. Для таблиц констант — as const satisfies T.

How do you make a switch over a union exhaustive, and why does never help?
In the default branch, assign the value to a variable of type never. When someone adds a new member to the union, this line stops compiling.
I write a small helper: `function assertNever(x: never): never`. In the default case of the switch I call it with the value. If all cases are handled, the value's type at that point is never, so it compiles. When a new variant is added to the union and not handled, the type is no longer never, and the build fails exactly at the switch that needs a new case. This is a cheap safety net for reducers and status rendering.
В default передаю значение в assertNever(x: never). Новый вариант union ломает компиляцию ровно там, где не обработан.

Enums vs a union of string literals vs an as const object?
Prefer a union of literals or an as const object. They have no runtime cost and work with all build tools. Numeric enums accept any number, and const enum breaks across module boundaries.
A union of string literals is only a type, so it costs nothing at runtime. When I also need the values in code, I write an object with as const and derive the type with `typeof Obj[keyof typeof Obj]`. TypeScript enums generate real objects. Numeric enums accept any number, which is unsafe. const enum is inlined by tsc but not by esbuild or Babel, and it does not work across package boundaries. Many teams simply forbid enums.
Предпочитаю union литералов или as const объект: ноль рантайма, работает со всеми сборщиками. Числовые enum небезопасны, const enum ломается на границах модулей и в esbuild.

Which strict flags matter most, and what does noUncheckedIndexedAccess change?
strict is the base. noUncheckedIndexedAccess makes arr[i] and obj[key] return T | undefined. exactOptionalPropertyTypes separates a missing field from undefined. verbatimModuleSyntax requires import type.
strict turns on null checks, no implicit any, strict function types and a few more. noUncheckedIndexedAccess says: an index access may give undefined, so handle it. It catches real bugs in loops and lookups, but adds some noise. exactOptionalPropertyTypes makes `{ a?: T }` different from `{ a: T | undefined }`. verbatimModuleSyntax forces me to write `import type` for types, so bundlers can drop those imports without running the type checker.
strict — база; noUncheckedIndexedAccess делает индекс T | undefined; exactOptionalPropertyTypes отличает отсутствие поля от undefined; verbatimModuleSyntax требует import type.

How do you type a generic React component, and what is the problem with forwardRef?
Write the generic on the function: `function Table<T>(props: TableProps<T>)`. forwardRef loses the generic unless you cast. In React 19 ref is a normal prop, so the problem is gone.
A generic component is just a generic function. When I write `<Table rows={users} />`, TypeScript infers T from the rows prop, and the render callbacks are typed. forwardRef returns a non-generic type, so the generic is lost. The old workaround was a cast or a module declaration. In React 19 function components receive ref as a normal prop, so forwardRef is not needed. For components with an `as` prop I use the ComponentPropsWithoutRef pattern.
Дженерик-компонент — дженерик-функция, T выводится из пропсов. forwardRef теряет дженерик (нужен каст); в React 19 ref — обычный проп.

Where does TypeScript stop protecting you at runtime, and what do you do about it?
Types disappear after compilation. Data from the network, storage, URL params and JSON.parse is really unknown. Validate it at the boundary with zod or valibot and take the type from the schema.
Everything that comes from outside is unknown at runtime: API responses, localStorage, query strings, messages from iframes. A cast like `as User` only makes the compiler quiet; it does not check anything. So I describe the data once with a zod or valibot schema, parse it at the boundary, and use z.infer to get the TypeScript type from the same schema. Then the type and the check can never disagree. In forms the same schema gives validation messages.
Типы исчезают в рантайме; сеть, storage, URL, JSON.parse — unknown. Валидирую на границе через zod/valibot и беру тип из схемы.

## React · Rendering internals

What happens between setState and the change on the screen?
React schedules an update with a priority. In the render phase it calls components and builds a new tree; this can be paused. In the commit phase it changes the DOM, runs layout effects, the browser paints, then useEffect runs.
When I call setState, React stores the update on that component with a priority and schedules work. In the render phase React calls the component functions, compares the result with the current tree and collects the changes. With concurrent features this phase can pause and continue later. The commit phase is synchronous: React changes the DOM, runs useLayoutEffect and ref callbacks. Then the browser paints. After that React runs useEffect callbacks. This is why render must have no side effects, and why layout effects block the paint.
setState → апдейт с приоритетом → render-фаза строит новое дерево (может прерываться) → commit синхронно меняет DOM → layout-эффекты → paint → useEffect.

What problem does concurrent rendering solve, and what are lanes?
A big render can be paused so that urgent work like typing is handled first. Lanes are priority levels for updates.
Before React 18, a big update blocked the main thread until it was done. With concurrent rendering React works for a few milliseconds, then checks if there is more urgent work, for example a key press, and handles it first. It can continue the big render later or start it again. Lanes are the priorities: user input is urgent, a transition is low priority, idle work is lowest. useTransition marks an update as low priority, so a heavy list does not delay the key press that caused it. The rule for us: render must be pure, because it may run more than once.
Конкурентный рендер прерывает тяжёлые обновления ради срочного ввода. Lanes — уровни приоритета. useTransition помечает обновление как неприоритетное; рендер должен быть чистым.

useTransition vs useDeferredValue vs debouncing — when do you use each?
useTransition when you call setState yourself. useDeferredValue when you receive a value from a parent. Debounce when you want fewer network requests, not just smoother rendering.
With useTransition I wrap my own setState call. The input updates right away, and the heavy list updates in the background. I also get isPending to show a spinner. useDeferredValue is for a value I do not control, for example a prop: React gives me a copy that updates when it has time. Both only help with rendering cost. If the cost is network requests, I still need debounce or request cancellation. Often I use both together.
useTransition — когда сам вызываю setState; useDeferredValue — для входящего значения. Оба про рендер; сетевые запросы требуют debounce и отмены.

Why does StrictMode run components and effects twice in development?
To show you impure renders and effects without cleanup before they break in concurrent mode. Effects run setup, cleanup, setup again.
In development StrictMode calls each component function two times and runs each effect as setup, then cleanup, then setup again. The double render shows side effects inside render, for example an API call or a ref change. The double effect shows subscriptions and timers that have no cleanup. These bugs would also appear when React keeps state during Fast Refresh or in future features. The fix is to make effects safe to run twice, not to remove StrictMode.
StrictMode дважды вызывает рендер и эффекты (setup→cleanup→setup), чтобы показать нечистый рендер и эффекты без cleanup до того, как они сломаются в конкурентном режиме.

How does Suspense work under the hood?
A component throws a promise. The nearest Suspense boundary catches it and shows the fallback. When the promise resolves, React renders again. The data source must cache the result so the second render gets it synchronously.
Suspense is built on throwing. When data is not ready, the component throws a promise-like object. React goes up to the nearest Suspense, shows the fallback and waits for the promise. When it resolves, React tries to render the component again. This time the data source must return the value right away from a cache. If it starts a new request again, the component suspends forever. That is why a plain fetch inside a component does not work, and why libraries like TanStack Query or the React 19 use hook with a stable promise are needed.
Компонент бросает промис, ближайший Suspense ловит и показывает fallback; после resolve рендер повторяется, источник данных должен отдать результат из кэша, иначе бесконечный suspend.

How does React decide to keep or recreate a component during reconciliation?
Same component type at the same position in the same parent, and the same key in a list. A different type or key unmounts the subtree and its state.
React compares the new tree with the old one, child by child, by position and type. This makes the algorithm fast. If the type changes, for example a div becomes a span, React removes the whole subtree and creates a new one. If the key changes, the old instance is unmounted and a new one is mounted. I use this on purpose: changing the key of a form resets it. A common bug: a component defined inside another component is a new type on every render, so its state resets every time.
Переиспользует при том же типе и позиции (и key в списке); иначе размонтирует вместе со стейтом. Смена key сбрасывает форму; компонент внутри компонента — новый тип каждый рендер.

What is tearing, and how does useSyncExternalStore prevent it?
Tearing: during one render, two components show two different versions of an external store, because the render was paused and the store changed. useSyncExternalStore detects this and forces a synchronous re-render.
With concurrent rendering a render can pause in the middle. If an external store, for example Redux, changes during the pause, components rendered later read the new value while earlier ones have the old value. For one frame the UI is inconsistent. useSyncExternalStore subscribes to the store and takes a snapshot. If the snapshot changed during render, React drops the result and renders again synchronously. Redux, Zustand and routers use this hook. It also has getServerSnapshot for SSR.
Tearing — в одном рендере две версии внешнего стора из-за паузы. useSyncExternalStore сравнивает снимок и форсирует синхронный рендер; его используют Redux, Zustand.

Why does a click inside a portal reach a React parent that is not its DOM parent?
React events go up the React tree, not the DOM tree. A portal is still a child in the React tree, so the parent's onClick fires.
React adds one native listener per event type on the root. When an event happens, React walks its own component tree, not the DOM tree. A modal rendered with createPortal into document.body is still a child of its React parent. So the parent's onClick sees clicks inside the modal, and context also works. The downside: a "click outside" check cannot use React propagation. It must check the DOM with element.contains or use a native listener.
Синтетические события всплывают по дереву React, а не DOM; портал остаётся ребёнком в React, поэтому родитель получает клики. Для click-outside нужна DOM-проверка.

What is automatic batching in React 18, and what does flushSync do?
React 18 groups all state updates in the same tick into one render, also in promises and timeouts. flushSync forces React to update the DOM right now.
In React 17 only updates inside React event handlers were batched. Two setState calls in a setTimeout caused two renders. With createRoot, every update in the same tick is batched, no matter where it comes from. Sometimes I need the DOM updated right away, for example to scroll to a new item after adding it. Then I wrap the setState in flushSync, and React commits synchronously. It is slower, so I use it rarely. Reading state right after setState still gives the old value, with or without batching.
React 18 батчит все обновления в одном тике (и в промисах, таймерах). flushSync форсирует синхронный коммит, например для скролла к новому элементу.

## React · Hooks & patterns

Why do effects see old props, and how do you read the latest value without re-subscribing?
A closure keeps the values of its own render. Keep the latest callback in a ref, or use useEffectEvent. Then the effect can have an empty dependency array and still call fresh logic.
An effect's function remembers the props and state of the render that created it. If I subscribe once with an empty array and call onMessage inside, I call the version from the first render forever. If I add onMessage to the dependencies, the effect re-subscribes on every render, which may be expensive or lose events. The pattern: keep a ref, update ref.current on every render, and call ref.current inside the effect. React's useEffectEvent does the same thing officially: it gives a stable function that always sees the current values and is not a dependency.
Эффект помнит значения своего рендера. Чтобы подписка жила с [] и видела свежий колбэк — ref с последним значением или useEffectEvent.

Callback refs vs useRef, and when do you need useImperativeHandle?
A callback ref runs when the DOM node appears or disappears, so it is good for measuring and observers. useRef is a box for a value. useImperativeHandle gives a parent a small API like focus().
useRef gives me a box that keeps a value between renders, but nothing happens when it changes. A callback ref is a function that React calls with the node on mount and with null on unmount. So I can start a ResizeObserver exactly when the element exists, even if it renders conditionally. useImperativeHandle lets a child expose a few methods to the parent, for example focus or scrollToRow, instead of giving the whole DOM node. I use it rarely. Data should go through props.
Callback ref срабатывает при появлении/удалении узла — для измерений и observers. useRef — хранилище. useImperativeHandle — маленький API (focus, scrollTo), редко.

Compound components, render props, HOCs and hooks — which problem does each solve today?
Hooks share logic. Compound components share state across flexible markup, like Select and Select.Option. Render props give the consumer control over rendering. HOCs are mostly old style.
Hooks replaced most higher-order components and render props for logic reuse, because they compose without extra wrappers. Compound components use context: the parent owns the state and the consumer places the parts freely. Radix and Headless UI work this way. Render props are still the cleanest way to let the consumer decide how to render something, for example a virtual list asks how to render one row. HOCs still appear for things like withAuth around a route.
Хуки — переиспользование логики; compound components — общий стейт при свободной разметке (Radix); render props — отдать рендер потребителю; HOC — почти не используются.

What is derived state, and why is copying props into state with useEffect a bad idea?
State that can be computed from other state or props should be computed during render, not stored. Copying gives one extra render with old data. To reset state, change the key.
If filteredItems can be computed from items and query, storing it in state is a mistake. It needs an effect, the effect runs after render, so for one frame the UI shows old data, and then there is a second render. I compute it during render, with useMemo if it is expensive. When a parent prop should reset the local state, I change the key of the component instead of writing an effect. Effects are for syncing with something outside React, not with other state.
Производное состояние считается в рендере (useMemo при необходимости), а не копируется через useEffect — лишний рендер и устаревший кадр. Сброс — через key.

When does React.memo not help, and how do you make it work?
It fails when a prop is a new object, array, function or JSX on every render. Fix it with useMemo and useCallback in the parent, pass primitives, or move the state down.
React.memo compares props one by one with ===. Any prop that is a new reference breaks it: an inline style object, an inline arrow function, items.filter() in the parent, or JSX children. I can make these references stable with useMemo and useCallback. I can pass primitive values instead of objects. Or I can restructure: move the state into the component that needs it, or pass the heavy part as children from a parent that does not re-render. First I measure with the Profiler; memo everywhere is not a plan.
memo ломается от новых ссылок в пропсах (объекты, inline-функции, children). Стабилизировать ссылки, передавать примитивы или перенести стейт ниже.

What does the React Compiler do, and what should you stop doing when it is on?
It memoizes components and hooks automatically. Manual useMemo, useCallback and memo become mostly unnecessary. The code must follow the rules: no mutation of props or state, no side effects in render.
The compiler reads the component and adds memoization itself, based on which values a piece of JSX or a callback really depends on. It is like an automatic and correct useMemo everywhere. It can only do this for code that follows the rules of React: no side effects in render, no mutation of props or state, hooks called in the same order. The ESLint plugin shows violations, and the compiler skips such components. In practice I delete most manual memoization and keep the code pure.
Компилятор сам мемоизирует компоненты и хуки; ручные useMemo/useCallback почти не нужны. Требует чистого кода без мутаций; нарушители пропускаются.

How do you design state for a big form?
Uncontrolled inputs with a form library like react-hook-form. No re-render on every key press, validation with a zod schema, Controller only for custom components.
Controlled inputs re-render the form on every key press. For a few fields it is fine. For fifty fields it is slow. react-hook-form registers inputs through refs, so the browser keeps the values and React renders only when needed. It connects to zod for validation, and the types come from the same schema. For custom components like a date picker I use its Controller wrapper. The form state has the same shape as the API payload, so submit is simple.
Для больших форм — неконтролируемые инпуты через react-hook-form + zod: нет рендера на каждый символ, типы из схемы; Controller — для кастомных компонентов.

How do you stop a context from re-rendering the whole app, and when do you move to a store?
Split contexts by how often they change, memoize the provider value, put setters in a separate context. When many components need small parts of fast-changing state, use a store with selectors.
Every consumer re-renders when the context value changes, and the value is often a new object each time. So I split: theme and user change rarely, cursor position or a draft change often. I wrap the value in useMemo. I put dispatch or setters in their own context, so components that only write do not re-render on reads. Context has no selectors. When I need state.cart.count without re-rendering on state.filters, I move to Zustand or Redux, where a selector subscribes to one slice.
Разделять контексты по частоте изменений, мемоизировать value, сеттеры в отдельный контекст. Нет селекторов — при частых срезах переходить на Zustand/Redux.

## React · Data & state

Server state vs client state — why treat them differently?
Server state is shared, async and can be old. The backend owns it. Client state is local and synchronous. Use a query cache for the first, plain state or a small store for the second.
Data from an API has a life cycle: loading, error, fresh or stale, refetch, invalidation, pagination. Writing all this by hand in Redux gives a lot of boilerplate. A query library like TanStack Query or RTK Query does it with keys, staleTime, retries and background refetch. Real client state is small: is the modal open, which tab is selected, what the user typed in a form. For that, useState, URL params or a small store are enough. Mixing the two is the most common architecture problem I see.
Серверное состояние — общее, асинхронное, устаревает; его ведёт query-кэш (TanStack/RTK Query). Клиентское — модалки, вкладки, формы — useState, URL, маленький стор.

How do you implement optimistic updates safely?
Cancel running queries, save the old cache, write the expected result, send the mutation. On error, restore the old data. On finish, refetch so the server wins.
In TanStack Query the pattern is onMutate: cancel refetches for this key, save the current data, and write the new value into the cache. onError puts the saved data back and shows a message. onSettled invalidates the query, so the real server response fixes any difference. I do this only for actions that almost always succeed and have a clear UI, like a like button. Never for payments. If the mutation can be retried, I add an idempotency key.
onMutate: отменить refetch, снимок кэша, записать ожидаемое; onError — откат; onSettled — invalidate. Только для надёжных действий, не для платежей; idempotency key.

How do you avoid request waterfalls and race conditions when fetching data?
Start requests in parallel, fetch at the route level, prefetch on hover. For races, cancel the previous request or ignore responses for an old input.
A waterfall happens when a child starts its request only after the parent's data arrives. The fix is to start requests together: Promise.all, parallel queries, or a route loader that fetches before the page renders. A race condition is when an old response arrives after a new one and overwrites it. The fix is to abort the previous request in the effect cleanup, or to compare a request id before setting state. Query libraries do both: they deduplicate by key and keep only the latest result.
Водопады — фетчить параллельно и на уровне роута; гонки — abort предыдущего запроса в cleanup или сравнение id запроса. Query-библиотеки делают это по ключу.

When do you refetch, invalidate or update the cache by hand?
Invalidate lists after create or delete. Update the cache directly when the mutation returns the entity. Use a long staleTime for data that rarely changes. Refetch on window focus for shared data.
I start from the nature of the data. Reference data like countries gets a long staleTime. After I create or delete an item, I invalidate the list queries so pagination stays correct. After an edit, I write the returned entity into the detail cache and patch the item in the list, so the user does not see a flash. Refetch on window focus is on for dashboards that other people edit and off for forms. The goal: the user never sees data older than acceptable, and we do not send useless requests.
Инвалидация списков после мутаций; прямое обновление кэша, когда мутация возвращает сущность; большой staleTime для справочников; refetch on focus для общих данных.

How does Zustand avoid re-renders, and how is it different from Redux?
The store lives outside React. A component subscribes with a selector and re-renders only when the selected part changes. Redux does the same with useSelector but adds reducers, actions, middleware and devtools.
Zustand's store is a plain object with a subscribe function. When I write `useStore(s => s.count)`, the component re-renders only when count changes. There is no provider and no action types. Redux Toolkit uses the same selector idea, but adds structure: immutable reducers through Immer, serializable actions, time travel in devtools, middleware, and RTK Query. I choose Zustand for UI state in an app, and Redux Toolkit when the team wants strict structure or already uses it.
Zustand: стор вне React, подписка селектором, рендер только при смене среза. Redux — то же через useSelector плюс редьюсеры, действия, middleware, devtools.

What belongs in the URL, and how do you keep it in sync?
Anything the user may share, bookmark or restore after refresh: filters, page, sort, selected item, tab. Parse the params with a schema and write them back through the router.
If the user presses refresh and loses the filters, that is a bug. I keep filters, sort, page, the selected entity and the open tab in search params. I parse them with a zod schema that has defaults, and I write them back through the router. For a search input I use replace instead of push and a debounce, so the history does not fill up. The URL becomes the single source of truth, and the state can be shared and tested.
В URL — фильтры, пагинация, выбранный элемент, вкладка; парсить схемой с дефолтами, писать через роутер, replace + debounce для частых изменений.

How do you build infinite scroll with cursor pagination correctly?
useInfiniteQuery with a cursor from the server, a sentinel element watched by IntersectionObserver, virtualization for long lists, stable keys. New items at the top are a separate flow.
The server returns items and a nextCursor. A cursor is better than an offset, because the data may change while the user scrolls. I put an empty element at the end of the list and watch it with IntersectionObserver. When it becomes visible, I call fetchNextPage, with a hasNextPage check so I do not fetch twice. For thousands of rows I virtualize, so the DOM stays small. New items at the top are different: adding them moves everything down, so I must fix scrollTop after the insert.
useInfiniteQuery с курсором, sentinel через IntersectionObserver, виртуализация, стабильные ключи; новые элементы сверху — отдельный поток с коррекцией scrollTop.

## Next.js & SSR

Where is the server/client boundary in React Server Components, and what can cross it?
A file with 'use client' starts a client subtree. A server component can render a client component and pass it serializable props, including server JSX as children. Functions cannot cross, except server actions.
In the App Router every component is a server component by default. It can read the database directly and its code is never sent to the browser. 'use client' marks the start of an interactive part. Props that cross this border must be serializable: plain objects, arrays, strings, and JSX from the server as children. Functions, class instances and Dates do not pass, with one exception: server actions, which become RPC calls. A client component cannot import a server component; it can only receive it as a prop.
'use client' начинает клиентское поддерево; пропсы через границу — только сериализуемые (JSX как children можно, функции нет), кроме server actions.

Explain the Next.js caching layers and how you invalidate them.
Four layers: request memoization inside one render, the Data Cache for fetch between requests, the Full Route Cache for static pages, and the Router Cache in the browser. Invalidate with revalidatePath, revalidateTag or cache: 'no-store'.
Inside one request, the same fetch call is done only once. Between requests, the Data Cache keeps fetch results until the revalidate time passes or until I call revalidateTag, for example from a server action or a webhook. If all data on a page is cacheable, the page becomes static HTML in the Full Route Cache. In the browser, the Router Cache keeps visited segments for fast back navigation. When data looks old, I check which of the four layers served it. Since Next 15, fetch is not cached by default, which removes many surprises.
Четыре слоя: мемоизация в запросе, Data Cache между запросами, Full Route Cache для статики, Router Cache в браузере. Инвалидация — revalidatePath/Tag, no-store.

What causes hydration mismatches, and how do you fix them?
The server and the client rendered different HTML: Date.now, random values, locale, window checks, browser extensions, invalid HTML nesting. Move browser-only logic to useEffect or use dynamic import with ssr: false.
Hydration connects React to the HTML from the server and expects the same tree. If anything differs, React warns and may re-render from scratch. Common causes: text that depends on the current time, code that renders differently when window exists, date formatting that depends on the user's locale, a div inside a p that the browser moved, or an extension that changed the page. The fix: render a neutral placeholder on the server and update it in useEffect, use a mounted flag for browser-only widgets, and keep the locale the same on both sides. suppressHydrationWarning is only for a single text node like a timestamp.
Сервер и клиент дали разное: Date.now, window, локаль, расширения, невалидная вложенность. Лечить переносом в useEffect, флагом mounted, dynamic ssr:false; suppress — крайняя мера.

What does streaming SSR with Suspense change for the user and for the architecture?
The server sends the page shell first and streams the slow parts later. The user sees content sooner. You must put slow data behind Suspense boundaries and design the page in independent blocks.
Without streaming the server waits for the slowest query before sending anything. With streaming it sends the layout and the fallbacks right away, keeps the connection open, and sends the HTML of each block when its data is ready, with a small script that puts it in place. The user sees the page sooner, and the LCP metric improves. For this to work, I wrap each independent data block in its own Suspense and give the fallback the right size, so the layout does not jump.
Сервер сразу отдаёт оболочку с fallback-ами, медленные части достримливает. Лучше TTFB/LCP; нужно изолировать медленные данные в Suspense и держать размеры fallback.

How do server actions work, and what are the security risks?
A function with 'use server' becomes a POST endpoint. The client sends the arguments. Anyone can call this endpoint, so check the session, the permissions and the input inside the action.
On the client, a server action is replaced by a reference. Calling it sends a POST request with the arguments to Next, and the function runs on the server. It works with forms and useActionState even before JavaScript loads. Security-wise, a server action is a public API. So inside it I check the session again, check that this user may change this specific resource, validate the input with a schema, and never trust a hidden id from the form. Values captured by closures are encrypted, but I still do not put secrets there.
'use server' → POST-эндпоинт. Это публичный API: внутри проверять сессию и права, валидировать вход схемой, не доверять скрытым полям.

Edge runtime vs Node runtime — what can you do at the edge?
Edge runs close to the user, starts fast, but has only Web APIs: no Node modules, no file system, short CPU time. Use it for redirects, auth checks, A/B tests and headers. Database work stays in Node.
Edge functions run in many regions, so they are close to the user and start in milliseconds. This makes them good for small decisions before the request reaches the app: read a cookie, redirect a user who is not logged in, choose a language, set headers. The runtime is limited: fetch, Request, Response and crypto exist, but Node built-ins do not, and the CPU time is short. Anything that needs a database driver, an ORM or heavy computation runs in the Node runtime.
Edge — быстрый старт рядом с пользователем, только Web API, без Node-модулей: редиректы, auth, A/B, заголовки. База и тяжёлое — в Node runtime.

## Browser & Networking

How does the browser use layers, and why do transform and opacity animate smoothly?
Some elements get their own layer. The GPU can move a layer without redrawing it. transform and opacity change only the compositing step, while top, left or width force layout and paint again.
After painting, the browser splits the page into layers and the GPU puts them together. If I animate transform or opacity on an element with its own layer, only the compositing step changes. The main thread is free and the animation stays at 60 frames per second. If I animate width or top, the browser must calculate layout and paint again for the whole affected area. will-change creates a layer in advance, but too many layers use a lot of memory. The Layers panel in DevTools shows what is being repainted.
Слои двигает GPU; transform/opacity меняют только композицию, без layout и paint. will-change заранее создаёт слой, но слоёв не должно быть много.

preload, prefetch, preconnect, dns-prefetch, modulepreload — what does each do?
preload loads a resource for this page with high priority. prefetch loads something for the next page with low priority. preconnect opens the connection early. modulepreload preloads an ES module.
preload tells the browser about a resource it would find late, for example a font or the hero image. It must be used on the page, or the download is wasted. prefetch is a hint for the next navigation, done when the browser is idle. preconnect does the DNS lookup and the TLS handshake for another domain in advance; dns-prefetch does only the DNS part. modulepreload is preload for ES modules, and it also parses them. The fetchpriority attribute changes the order of downloads even more.
preload — критичный ресурс этой страницы; prefetch — для следующей, в простое; preconnect — соединение заранее; modulepreload — для ESM с парсингом.

How do Cache-Control, ETag, Last-Modified and immutable work together?
max-age says how long the response is fresh. After that, the browser asks the server with If-None-Match and gets 304 if nothing changed. Hashed files get one year and immutable. HTML gets no-cache.
While the response is fresh, the browser uses the cache without any request. When it expires, the browser sends a conditional request with the ETag or the date, and the server answers 304 Not Modified, which is cheap. For bundles with a hash in the file name I set max-age of one year and immutable, because the URL changes on every deploy. For HTML I set no-cache: it is still stored, but the browser always checks with the server, so a deploy is visible right away. stale-while-revalidate shows the old version while the new one downloads in the background.
max-age — свежесть; потом условный запрос по ETag → 304. Хэшированные бандлы — год + immutable; HTML — no-cache (всегда проверка); stale-while-revalidate для плавности.

What do you use service workers for, and what cache strategies do you combine?
A service worker is a network proxy in the browser: offline, caching, push. Precache the app shell, cache-first for hashed files, stale-while-revalidate for images, network-first for API data.
A service worker sits between the page and the network. It can answer a request from the cache, from the network, or both. With Workbox I precache the app shell at install time. Static files with hashes are served cache-first. Images use stale-while-revalidate. API calls use network-first with a cache fallback. The hard parts are updates and privacy. A new worker waits until all tabs are closed unless I call skipWaiting and tell the user. And I must never cache a page with private data by accident.
Прокси в браузере: precache оболочки, cache-first для хэшированных файлов, SWR для картинок, network-first для API. Сложное — обновление воркера и не кэшировать приватный HTML.

Explain the CORS preflight. When does it happen, and how do you avoid it?
The browser sends an OPTIONS request first when the request is not simple: PUT or DELETE, custom headers, or Content-Type application/json. The server answers with Access-Control-Allow headers. Access-Control-Max-Age caches the answer.
A simple request, like a GET or a form POST, goes directly, and the browser only checks the response headers. If the request has an Authorization header, a JSON content type, or a method like PUT, the browser first sends OPTIONS to ask for permission. This costs one extra round trip. The server must return the allowed origin, methods and headers. If cookies are used, it must also return Access-Control-Allow-Credentials, and then the origin cannot be a star. Access-Control-Max-Age caches the preflight. A proxy on the same origin, or a BFF, removes CORS completely.
Preflight OPTIONS — для non-simple запросов (JSON, Authorization, PUT/DELETE). Сервер отвечает Allow-*; с credentials нельзя *. Max-Age кэширует; BFF убирает CORS вовсе.

Cookie flags: HttpOnly, Secure, SameSite, Domain — what matters for auth?
HttpOnly: JavaScript cannot read the cookie, so XSS cannot steal it. Secure: only over HTTPS. SameSite=Lax blocks most CSRF but allows normal links. Strict is safer but breaks links from emails.
For a session cookie I set HttpOnly, Secure and SameSite. HttpOnly means that even if a script is injected, it cannot read the cookie. Secure means the cookie is sent only over HTTPS. SameSite=Lax means the cookie is not sent with cross-site POST requests, which blocks most CSRF, but it is sent when the user clicks a link to my site. Strict blocks even that, so a login link from an email opens a logged-out page. If the frontend and the API are on different domains, I need SameSite=None with Secure, CORS with credentials, and a CSRF token. Browsers now also partition third-party cookies by top site.
HttpOnly — не читает JS; Secure — только HTTPS; SameSite Lax блокирует CSRF, но пускает переходы по ссылке; разные домены → None + Secure + CSRF-токен.

WebSockets vs Server-Sent Events vs long polling — how do you choose?
SSE for a stream from the server to the client over normal HTTP, with automatic reconnect. WebSockets for two-way, low-latency traffic like chat. Long polling only as a fallback.
Server-sent events are a normal HTTP response that stays open. The browser reconnects automatically and sends the last event id. It works through proxies and with HTTP/2. It is perfect for notifications and for streaming AI text. WebSockets open a two-way connection. They are right when the client also sends many messages: chat, collaborative editing, games. But I must handle reconnect, heartbeats and back-pressure myself. Long polling is the fallback when the infrastructure blocks everything else.
SSE — поток сервер→клиент по HTTP с автопереподключением (уведомления, стриминг). WebSocket — двусторонний и быстрый (чат, коллаборация), но реконнект и heartbeats на мне.

What are Intersection, Resize and Mutation Observers, and what do they replace?
They report visibility, size and DOM changes asynchronously, in batches. They replace scroll and resize listeners that read getBoundingClientRect on every event and forced layout.
IntersectionObserver tells me when an element enters or leaves the viewport, without reading layout on every scroll event. It makes lazy loading and infinite scroll cheap. ResizeObserver tells me when the size of an element changes, which is how container-aware components work. MutationObserver tells me about DOM changes in batches, useful with third-party widgets. All three run asynchronously, so they do not cause layout thrashing.
IntersectionObserver — видимость (lazy load, бесконечный скролл), ResizeObserver — размер элемента, MutationObserver — изменения DOM; все асинхронные, без layout на каждом событии.

What do HTTP/2 and HTTP/3 change for bundling decisions?
HTTP/2 sends many files over one connection, so many small chunks are fine and old tricks like sprites and domain sharding are not needed. HTTP/3 works better on bad mobile networks. Fewer bytes still matter most.
With HTTP/1.1 the browser opened about six connections per domain, so we merged files into one big bundle. HTTP/2 sends many streams over one connection, so splitting the bundle into cacheable chunks is good: a small change does not invalidate everything. HTTP/3 runs over QUIC on UDP, so one lost packet does not block the other streams, which helps a lot on mobile. But bytes are still not free: the browser must download, parse and run the JavaScript.
HTTP/2 мультиплексирует — много мелких чанков выгодно для кэша; шардинг и спрайты не нужны. HTTP/3 на QUIC лучше на плохих сетях. Байты и парсинг JS всё равно главное.

## Performance

How do you find why a React page is slow, step by step?
Reproduce with CPU and network throttling. Use the Performance panel to find long tasks. Use the React Profiler to see which components render and why. Check the network for waterfalls. Fix the biggest problem, measure again.
First I reproduce the problem with CPU throttling and a slow network, like a real mid-range phone. The Performance panel shows where the time goes: scripting, layout or network, and marks long tasks over 50 milliseconds. If the problem is rendering, the React Profiler shows which components rendered, how many times and why. Often the cause is state high in the tree. If the problem is network, I look for waterfalls and large responses. I fix one thing, measure again, and keep a Lighthouse or Web Vitals number as the check against regressions.
Воспроизвести с троттлингом → Performance (long tasks) → React Profiler (кто и почему рендерится) → сеть (водопады, размеры) → чинить самое крупное и перемерять.

What is INP, and what usually makes it bad?
Interaction to Next Paint: the delay from a user action to the next frame, measured over the whole visit. Causes: long JavaScript in click handlers, big React commits, synchronous layout reads, third-party scripts.
INP replaced FID. It measures almost the worst interaction during the whole page life, not just the first one. A bad INP usually means that a click handler does too much work at once, or a state change re-renders a huge tree, or code reads layout right after changing the DOM. The fixes: break long work into pieces with scheduler.yield or setTimeout, move non-urgent updates into startTransition, virtualize long lists, and move third-party scripts to a worker with Partytown.
INP — задержка от действия до следующего кадра за весь визит. Причины: долгие обработчики, тяжёлые коммиты, синхронные чтения layout, сторонние скрипты. Лечить yield, startTransition, виртуализацией.

How do you split the code, and what stays in the main bundle?
Split by route and by heavy features that are used rarely: editor, charts, maps. Keep the shell and the first screen together. Prefetch likely routes on hover or when idle. Do not make too many tiny chunks.
Route-based splitting with React.lazy or the framework's loader is the base. Then I split big libraries that are not needed at the start: a rich text editor, a chart library, a PDF viewer. A separate vendor chunk for stable dependencies helps caching. Too many small chunks create request chains and duplicated code, so I check the bundle analyzer and the network waterfall. Prefetching a chunk on hover or with requestIdleCallback hides the loading delay.
Делить по роутам и тяжёлым редким фичам (редактор, графики, карты); оболочку держать вместе; vendor-чанк для кэша; префетч по hover/idle; не дробить слишком мелко.

How do you optimize images and fonts for Core Web Vitals?
srcset with modern formats, width and height to avoid layout shift, lazy loading below the fold, preload for the main image. Self-host fonts, preload the main one, use font-display and tuned fallback metrics.
The main image is usually the LCP element, so I give it fetchpriority="high" and a preload. Everything below the fold gets loading="lazy". srcset and sizes give each screen the right resolution, and AVIF or WebP cuts the size in half. Width and height attributes reserve space, so nothing jumps when the image loads. For fonts I host woff2 files myself, preload the main one, use only a few weights, and tune the fallback font metrics with size-adjust, so the text does not jump when the real font arrives.
Главная картинка — preload и fetchpriority high, остальное lazy; srcset/sizes, AVIF/WebP, width/height против CLS. Шрифты self-host woff2, preload, font-display и подгонка fallback.

When is memoization harmful, and how do you decide?
Every useMemo and useCallback costs memory and a comparison, and wrong dependencies create bugs. Memoize only when the Profiler shows an expensive computation or a child that re-renders because of a changed reference.
Memoization is not free. React stores the previous value, compares the dependencies on every render, and the code becomes harder to read. For cheap computations it costs more than it saves. I add it when the Profiler shows a real cost, or when a memoized child or an effect needs a stable reference. With the React Compiler the picture changes, because memoization becomes automatic and correct.
Мемоизация стоит памяти и сравнений, ошибочные deps дают баги. Применять по профилю: дорогие вычисления или стабильная ссылка для memo-ребёнка. С React Compiler — автоматически.

How do you find and fix layout thrashing?
Reading layout (offsetHeight, getBoundingClientRect) right after writing styles forces the browser to calculate layout immediately. In a loop this happens many times. Read everything first, then write.
When I change a style and then read a layout property, the browser must calculate the layout right now to give the correct answer. If I do this in a loop over 100 elements, that is 100 layout calculations. In the Performance panel they appear as purple Layout blocks with a "forced reflow" warning. The fix: first read all values, then do all writes. ResizeObserver can replace manual measuring, requestAnimationFrame can group the writes, and often CSS can do the job without JavaScript.
Чередование чтений (offsetHeight) и записей форсирует reflow на каждом шаге. Сначала все чтения, потом записи; rAF, ResizeObserver, CSS вместо измерений в JS.

Virtualization vs pagination — what are the trade-offs?
Virtualization renders only the visible rows, so the DOM stays small, but it makes accessibility, find-in-page and variable heights harder. Pagination is simpler and better for SEO. Feeds use infinite query plus virtualization.
With a few thousand rows the DOM itself becomes slow. Virtualization renders only the rows in view plus a small buffer, positioned absolutely inside a container with the full height. The costs: rows with different heights must be measured, screen readers lose context, Ctrl+F does not find hidden rows, and scroll restoration is harder. For tables that users scan, normal pagination is often better and cheaper. Feeds get infinite query, and virtualization when they grow.
Виртуализация держит DOM маленьким, но усложняет a11y, поиск по странице, переменную высоту. Пагинация проще и лучше для SEO. Ленты — infinite query + виртуализация.

## CSS & Layout

What is a stacking context, what creates one, and why does z-index sometimes not work?
A stacking context is a group of elements that are layered together. position with z-index, opacity below 1, transform, filter and isolation create one. z-index works only inside the same context.
z-index is not global. An element with position and a z-index, or with transform, opacity below one, filter, or isolation: isolate, creates its own stacking context. All its children are layered inside it. So a child with z-index 9999 cannot go above a sibling of its parent if the parent's context is below. When a dropdown is hidden behind a header, I look at the ancestors to find the context. The reliable fix is a portal to body plus a small documented scale of z-index values.
Контекст наложения создают position+z-index, transform, opacity<1, filter, isolation. z-index сравнивается только внутри контекста. Выпадашки — через портал и шкалу z-index.

What is the containing block? Why does height: 100% often do nothing, and why does position: fixed sometimes scroll?
An absolute element is positioned relative to the nearest positioned ancestor. Percentages are relative to the containing block. A transform or filter on an ancestor makes a fixed element behave like absolute.
For an absolutely positioned element, the containing block is the nearest ancestor with a position other than static. For a normal element it is the nearest block container. For a fixed element it is the viewport. But if an ancestor has transform, filter, perspective or contain, it becomes the containing block, and the fixed element scrolls with it. A percentage height needs a defined height on the containing block, so height: 100% does nothing until every parent in the chain has a height.
Абсолют — от ближайшего позиционированного предка; проценты — от containing block; transform/filter на предке превращает fixed в absolute относительно него.

Container queries, cascade layers and :has — how do they change your CSS?
Container queries style a component by the width of its container, not the viewport. @layer orders groups of styles so specificity fights stop. :has selects a parent by its children without JavaScript.
Container queries let a card change its layout when its container is narrow, no matter how wide the window is. This is what design systems always needed. Cascade layers let me order resets, framework styles, components and utilities, so a utility class always wins without !important. This is how Tailwind and design systems avoid specificity wars. With :has I can style a form field when its input is invalid, or a card that contains an image. All three are supported in all modern browsers.
Container queries — стиль по ширине контейнера, не окна; @layer упорядочивает слои без войны специфичности; :has — стиль по потомкам без JS.

CSS custom properties vs Sass variables vs runtime CSS-in-JS — what is the modern setup?
Custom properties are live, inherit, and can change at runtime for themes. Sass variables disappear at build time. Runtime CSS-in-JS costs on every render and does not work in Server Components, so zero-runtime tools replace it.
Design tokens are best as CSS custom properties. They cascade, they can change per theme or per component, and JavaScript can read them with getComputedStyle. Sass variables are static; they are fine for math at build time. Runtime CSS-in-JS like styled-components injects styles during render, which costs performance and does not work in React Server Components. So the ecosystem moved to compile-time tools: vanilla-extract, Panda CSS, Tailwind. Same developer experience, no runtime cost.
Токены — CSS-переменные (живые, тематизируемые). Sass — статика на сборке. Runtime CSS-in-JS тормозит и не работает в RSC; тренд — zero-runtime (vanilla-extract, Panda, Tailwind).

How do you build a fast and accessible animation?
Animate only transform and opacity, use will-change rarely, respect prefers-reduced-motion, keep UI animations 150–300 ms. Use the Web Animations API or View Transitions for complex sequences.
Transform and opacity are handled by the compositor, so the animation stays smooth even when the main thread is busy. I do not animate height or layout properties. For expand and collapse I use grid-template-rows or measure once and animate transform. prefers-reduced-motion must turn motion off or make it shorter for users who need it. The Web Animations API gives me promises and play, pause and reverse. The View Transitions API animates between two states of the page with very little code.
Только transform/opacity, will-change дозированно, prefers-reduced-motion обязательно, 150–300 мс. WAAPI — контроль и промисы, View Transitions — переходы между состояниями.

Logical properties and modern layout — how do you support RTL and responsive design without many media queries?
margin-inline, padding-block and inset flip automatically for RTL. clamp() gives fluid font sizes and spacing. Grid with auto-fit and minmax, and flex-wrap, adapt without breakpoints.
Logical properties replace left and right with start and end, so Arabic and Hebrew layouts flip for free. clamp() gives a font size that grows smoothly between a minimum and a maximum. `grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr))` builds a responsive card grid in one line. aspect-ratio, gap and fit-content remove many wrapper divs. Media queries are then needed only for real layout changes, not for every width.
Логические свойства (inline/block) дают RTL бесплатно; clamp() — плавная типографика; grid auto-fit/minmax и flex-wrap — адаптив без брейкпоинтов.

## Architecture & Design

How do you organize a large frontend codebase so it stays maintainable?
Group by feature, not by file type. Allow imports only in one direction: shared → entities → features → pages. Enforce it with a lint rule. Each module has a small public API through an index file.
Folders like components, hooks and utils do not scale, because every feature touches all of them. I group code by feature, with layers, and allow imports only downward. A lint plugin like eslint-plugin-boundaries or the Feature-Sliced Design rules enforce this. Each feature exports a small public API, so I can refactor inside without breaking others. Shared UI lives in a design system package. Tests and styles live next to the code. This makes ownership clear and code splitting natural.
Структура по фичам, слои с направлением зависимостей (shared→entities→features→pages), линт на импорты, публичный API модуля через index, тесты рядом.

Micro-frontends: when are they worth it, and how would you integrate them?
Only when independent teams need to deploy independently. Integrate with Module Federation or import maps, share the design system and auth, keep state and styles isolated.
Micro-frontends solve a team problem, not a technical one: several teams want to ship on their own schedule. The price is high: duplicated dependencies, inconsistent UX, hard routing between apps, and slower pages. If I do it, I use Module Federation or native import maps with a shell app, share React and the design system as singletons, communicate through the URL and a small event contract, and keep CSS scoped. For one team or a few teams, a monorepo with separate packages is usually the better choice.
Оправданы, когда независимые команды нуждаются в независимых деплоях. Интеграция: Module Federation/import maps, общая дизайн-система и auth, изолированные стейт и стили. Часто монорепо лучше.

How do you design the API layer of a frontend app?
One typed client generated from the OpenAPI or GraphQL schema. Interceptors for auth and errors. A query layer on top. Mappers so the UI does not depend on raw backend shapes.
I generate types and a client from the schema, so when the backend changes the contract, the build fails instead of the user. One place handles the base URL, token refresh, error normalization and tracing headers. On top of it I use TanStack Query with a key factory per entity. If the backend shapes are not convenient, a small mapper converts them to frontend models, so a backend rename touches one file. Mock Service Worker uses the same contract for tests and local development.
Типизированный клиент из OpenAPI/GraphQL, перехватчики auth/ошибок, сверху query-слой с фабриками ключей, мапперы в модели фронта; MSW на том же контракте.

How do you handle errors and loading states consistently across the app?
Group errors by type: network, validation, auth, unexpected. Each type gets its own UI. Use error boundaries per region with a retry button, skeletons with the right size, and send unexpected errors to monitoring.
I define an error model early. A 401 means re-login. A 403 shows a permission screen. Validation errors go to the form fields. Network errors offer a retry. Unknown errors show a friendly message and go to monitoring with context. Error boundaries wrap independent parts of the page, so one broken widget does not kill the whole page. For loading I use skeletons with reserved size, so nothing jumps, and I load data at the route level to avoid a chain of spinners.
Классификация ошибок → свой UI для каждой (reauth, права, поля формы, retry, fallback). Boundaries по регионам, скелетоны с размерами, неожиданное — в мониторинг с контекстом.

How do you ship risky UI changes safely?
Feature flags with gradual rollout and a kill switch. Canary deploys. Error rate and Web Vitals per release. A/B tests with a clear metric. Flags must be removed after the rollout.
A flag service decides per user or per percentage, so I can deploy the code dark and turn it on first for the team. I watch the error rate, INP and conversion split by the flag. The kill switch turns the feature off without a deploy. Source maps are uploaded, so monitoring points to real code. Every flag has an owner and a removal date; otherwise the code fills with dead branches.
Фича-флаги с постепенным раскатом и kill switch, канарейки, мониторинг ошибок и Web Vitals по релизу, A/B с метрикой; флаги удалять после раскатки.

How do you build design-system components that are accessible, themeable and hard to misuse?
Headless primitives like Radix or React Aria for behaviour and accessibility, tokens as CSS variables, typed variants, composition instead of many boolean props, Storybook with visual tests.
I do not write keyboard and ARIA logic for a dropdown myself; I take a headless library and add styles. Colors, spacing and fonts are CSS variables, so a theme switch does not re-render anything. Variants are typed, so size="xl" fails at compile time if it does not exist. Instead of props like isPrimary, isLarge and isIcon, I use slots and children. Storybook with interaction tests and visual snapshots catches regressions, and the stories are the documentation for designers.
Headless-примитивы для поведения и a11y, токены в CSS-переменных, типизированные варианты, композиция вместо кучи boolean-пропсов, Storybook + визуальные тесты.

What breaks when you add a second language late?
Hardcoded strings, strings glued together, plural forms, date and number formats, longer text in layouts, RTL, sorting. Use ICU messages, Intl APIs and logical CSS from day one.
Late internationalization is expensive. Strings are everywhere, and sentences are built by gluing parts, which breaks word order in other languages. ICU MessageFormat handles plurals and gender. Intl.DateTimeFormat, Intl.NumberFormat and Intl.RelativeTimeFormat format values per locale. Intl.Collator sorts correctly. Layouts must survive German text that is 30 percent longer, and RTL mirroring through logical properties. Locale files are loaded lazily, so the main bundle stays small.
Ломаются склейка строк, множественное число, форматы дат/чисел, длина текста, RTL, сортировка. ICU, Intl.*, логический CSS, вынос строк с первого дня.

## Security & Quality

How do you add a Content Security Policy to a React app without breaking it?
Start in Report-Only mode. Use nonces or hashes for scripts instead of unsafe-inline, add strict-dynamic for chunks, limit connect-src and frame-ancestors, then switch to enforce.
A strict CSP blocks inline scripts, so most XSS payloads do not run even if an injection happens. The server generates a nonce for each request and puts it on the script tags. strict-dynamic allows scripts that are loaded by a trusted script, which is how bundler chunks work. connect-src limits where fetch can send data. frame-ancestors replaces X-Frame-Options and stops clickjacking. I start with Content-Security-Policy-Report-Only and a report endpoint, see what would break, fix it, and only then enforce.
Сначала Report-Only; nonce/hash вместо unsafe-inline, strict-dynamic для чанков; connect-src и frame-ancestors; потом enforce.

Where do you store access and refresh tokens in the browser, and why?
Refresh token in an HttpOnly, Secure, SameSite cookie. Access token in memory, not in localStorage. Better: a backend-for-frontend that keeps tokens on the server and gives the browser only a session cookie.
Any script that gets injected can read localStorage, so a token there means account takeover. I keep the short-lived access token in a JavaScript variable, which limits the damage. The refresh token goes into an HttpOnly cookie, so JavaScript cannot read it; the refresh endpoint then needs CSRF protection. The cleanest option is a BFF: the browser has only a session cookie, and the server holds the OAuth tokens and calls the APIs.
Refresh — в HttpOnly Secure SameSite cookie, access — в памяти, не в localStorage; лучше BFF: у браузера только сессионная кука, токены на сервере.

How do you protect a frontend from a malicious npm package?
Lock file and npm ci, review updates, audits and scanners, as few dependencies as possible, ignore-scripts in CI, SRI and CSP for CDN scripts.
Most attacks come through transitive dependencies or a stolen maintainer account. I commit the lock file and install with npm ci, so CI gets exactly what I reviewed. I run npm audit and a scanner like Socket that flags install scripts and network access in packages. I update in batches and read changelogs. In CI I install with --ignore-scripts, which blocks the most common payload. For scripts from a CDN I use Subresource Integrity and a CSP. And I keep the number of dependencies small from the start.
Lock-файл и npm ci, аудит и сканеры, минимум зависимостей, ignore-scripts в CI, читать changelog; для CDN — SRI и CSP.

Clickjacking, open redirects and tabnabbing — what are they, and how do you prevent them?
Clickjacking: your page is shown in an invisible iframe; block with frame-ancestors. Open redirect: a ?next= URL points to an attacker site; allow only relative paths. Tabnabbing: a new tab controls the opener; use rel=noopener.
In clickjacking an attacker puts my site into an invisible iframe and makes the user click on it. I forbid framing with the CSP frame-ancestors directive. In an open redirect, the login page sends the user to whatever is in ?returnTo, so an attacker can send users to a phishing site. I accept only relative paths from an allowlist. In tabnabbing, a page opened with target=_blank gets window.opener and can change my page. Modern browsers add noopener by default, but I still set rel="noopener" explicitly.
Фрейминг — frame-ancestors; редирект по ?next — только относительные пути из allowlist; target=_blank — rel=noopener.

How do you render user HTML or markdown safely in React?
Never use dangerouslySetInnerHTML with untrusted HTML. Sanitize with DOMPurify and an allowlist, or parse markdown to an AST and render React elements. Check link URLs for javascript: schemes.
React escapes text by default, so XSS enters through dangerouslySetInnerHTML, through links with a javascript: URL, or through third-party widgets. For user HTML I run DOMPurify with a strict allowlist, on the client and ideally also on the server, and I force rel and target on links. For markdown I parse it into an AST and render my own components, which gives both safety and control. CSP and Trusted Types add another layer of protection.
Без dangerouslySetInnerHTML для чужого HTML; DOMPurify с allowlist (и на сервере), markdown — через AST в компоненты, проверка схем ссылок; плюс CSP и Trusted Types.

## Testing

What do you test at each level of the frontend testing trophy?
Static checks (TypeScript, ESLint) catch typos. Unit tests cover pure logic and hooks. Integration tests with Testing Library and MSW are the biggest layer. A few E2E tests with Playwright cover the critical flows.
Types and lint are the cheapest layer and catch a surprising number of bugs. Unit tests cover reducers, utils and complex hooks. Most of my tests are integration tests: I render a feature with a real store and router, mock the network with MSW, and check what the user sees. E2E tests run the important flows, like login and checkout, against a real build; they are slow and sometimes flaky, so there are only a few. I avoid snapshot tests of markup: they fail on every change and prove nothing.
Статика (TS, lint) → unit для чистой логики → интеграционные с Testing Library и MSW как основной слой → немного E2E на критичные пути. Снэпшоты разметки — нет.

How do you test a custom hook and a component that loads data?
renderHook with a wrapper that provides the QueryClient. For components, MSW handlers return realistic data; use findBy and waitFor; test loading, success and error. Do not mock fetch directly.
For a hook I use renderHook and a wrapper with the providers it needs, then I call the returned functions inside act and check the result. For a data component I start an MSW server with handlers for the endpoints, render the component with a fresh QueryClient with retries off, and use findByText to wait for the loaded state. The error case comes from a handler that returns 500. These tests survive a change from fetch to axios or to a generated client, because they test behaviour, not implementation.
renderHook с wrapper провайдеров; компоненты с данными — MSW с реалистичными ответами, свежий QueryClient без ретраев, findBy/waitFor, ветки loading/success/error.

Why are E2E tests flaky, and how do you make them stable?
Hidden races: checking before the UI is ready, tests sharing data, slow networks, animations. Use auto-waiting locators, separate test data per test, mock external services, disable animations, keep traces on failure.
Flakiness is almost always a hidden race. A test checks the text before the UI has finished, or two tests use the same user, or a third-party service is slow. Playwright locators wait automatically, so I never use fixed sleeps. Each test creates its own data through an API or a fixture and cleans up after itself. I mock external services and freeze time when needed. Retries hide problems, so I track flaky tests and fix them. Traces and videos on failure make CI problems easy to debug.
Флаки — скрытые гонки: ждать по локаторам, отдельные данные на тест, мок внешних сервисов, выключить анимации, ретраи только как сигнал, трейсы на падении.

How do you test accessibility, and what cannot be automated?
axe in unit and E2E tests finds about a third of the problems: contrast, missing labels, wrong roles. Keyboard navigation, focus order and screen-reader announcements must be tested by hand.
Automated checks with jest-axe or the Playwright axe plugin find structural problems and can fail the build. That is cheap, so I always do it. But most real barriers are about flow: can I fill the form with Tab and Enter, does the focus move into the modal and come back after it closes, does the screen reader announce the result. I test the critical flows with the keyboard only and with VoiceOver or NVDA. In unit tests I query by role, which keeps components accessible as a side effect.
axe в unit и E2E ловит треть проблем автоматически; клавиатура, порядок фокуса, объявления скринридера — только руками. Запросы по role в тестах держат a11y.

## Scenarios & live coding

The app gets slower the longer the tab stays open. How do you investigate?
Probably a memory leak or a store that only grows. Watch the memory graph, take heap snapshots over time, look for listeners, intervals and subscriptions without cleanup, and caches that never delete.
I use the app for a while and watch the memory graph in the Performance monitor. If it goes up in steps and does not come down after garbage collection, it is a leak. I take a heap snapshot, repeat one action several times, take another snapshot, and compare: which objects grew and who holds them. Common causes in React: subscriptions without cleanup, a query cache with infinite gcTime, a Redux list that keeps every page, and third-party widgets that keep removed DOM nodes. Then I add a test or a memory budget in CI.
Похоже на утечку: график памяти, heap snapshots до/после повторяемого действия, retainers; подписки без cleanup, кэш без gcTime, бесконечно растущий стор.

A search box sends a request on every key press and sometimes shows results for an old query. Fix it properly.
Debounce the input, cancel the previous request with AbortController or let the query library handle it by key, ignore responses that do not match the current input, and keep the old results visible while loading.
There are three problems here: too many requests, responses in the wrong order, and a flickering UI. A debounce of 200 to 300 milliseconds cuts the requests. Cancelling the previous request in the effect cleanup, or using a query keyed by the search text, guarantees that only the latest result is shown. keepPreviousData or useDeferredValue keeps the old results on screen while the new ones load. I also handle the empty query and a minimum length.
Debounce, отмена предыдущего запроса (AbortController или ключ запроса), игнорировать несовпадающие ответы, keepPreviousData/useDeferredValue против мигания.

Design a reusable Autocomplete component. What do you think about beyond the happy path?
Keyboard and the ARIA combobox pattern, debounced async loading with cancel, controlled and uncontrolled value, a generic item type, portal rendering, virtualization, loading, empty and error states.
I start from the WAI-ARIA combobox pattern: the right roles, aria-activedescendant, arrow keys, Escape and Enter. The API takes an async loader that receives an AbortSignal, and a debounce option. It supports both controlled and uncontrolled value. Items are rendered through a render prop, so the component is generic over the item type. The list renders in a portal, so overflow and stacking contexts do not hide it, and it virtualizes when long. It shows loading, empty and error states. Tests cover the keyboard flows and race conditions.
ARIA combobox и клавиатура, асинхронная загрузка с debounce и отменой, controlled/uncontrolled, дженерик по типу элемента, портал, виртуализация, состояния loading/empty/error.

Design a dashboard that shows live data for thousands of users. What is your architecture?
The server pushes updates over SSE or WebSocket into a normalized store. Group updates per frame. Virtualize tables and charts. Pause when the tab is hidden. Refetch a full snapshot from time to time.
Updates can arrive faster than React can render, so I collect them in a buffer and apply them once per frame with a single state update. The store is normalized by id, so one update changes one row, and components subscribe with selectors. Tables and charts are virtualized or drawn on canvas. When the tab is hidden, I stop rendering and let the buffer collapse to the latest values. A periodic full snapshot from the server repairs any missed events, and the connection reconnects with backoff.
Push через SSE/WebSocket в нормализованный стор, батчить обновления по кадру, селекторы, виртуализация/canvas, пауза в скрытой вкладке, периодический полный снимок, reconnect с backoff.

How do you plan a migration from class components to hooks and TypeScript in a large codebase?
Step by step. Turn on TypeScript with allowJs and loose settings. Convert leaf components first. Use codemods for mechanical changes. Write tests before refactoring. Never a big rewrite.
The app must stay shippable all the time. TypeScript goes in with allowJs and strict off, then I turn on strict flags folder by folder. Class components are converted when someone touches them or by risk, starting from the leaves, because they have fewer dependencies. Codemods handle imports and simple patterns. Testing Library tests written before the conversion protect the behaviour. A simple progress dashboard shows the team that the migration moves and has an end date.
Пошагово: TS с allowJs и мягкими флагами, ужесточать по папкам; конвертировать с листовых компонентов, кодмоды, тесты до рефакторинга, без big-bang.

How do you approach a live-coding task in an interview?
Repeat the task in your own words, ask about edge cases, say your plan and its complexity, write a simple working version first, test it out loud with examples, then clean up and talk about trade-offs.
I repeat the task in my own words and ask about inputs, size of data and edge cases. Then I say my plan and its complexity before I type. I write the simplest correct version first. I run it in my head with two or three examples, including an empty input. Only then I improve names and structure. All the time I say what I am doing and why. At the end I say what I would add for production: tests, error handling, accessibility, performance.
Уточнить требования и крайние случаи, озвучить план и сложность, написать рабочую версию, прогнать примеры вслух, затем рефакторинг и trade-offs, что добавил бы в продакшене.

## Algorithms for live coding

Which data structure gives O(1) lookups in JavaScript, and when do you pick Map over an object?
Map and Set are hash tables with O(1) average operations. Use Map when keys are not strings, when order matters, when you add and delete a lot, or when keys come from the user.
A plain object also works as a hash map, but keys become strings, integer-like keys are ordered specially, and a user key like __proto__ is dangerous. A Map keeps any key type, remembers insertion order, has a size property and is faster with many inserts and deletes. A Set is for removing duplicates and for membership checks. Many interview tasks, like two sum, grouping anagrams or counting, are one Map away.
Map/Set — O(1) в среднем; Map вместо объекта, когда ключи не строки, важен порядок, много вставок/удалений или ключи от пользователя (нет __proto__).

Two pointers and sliding window — when do you use them?
For sorted arrays and for problems about pairs or contiguous parts. Two pointers move from both ends or in one direction. A sliding window keeps a running state over a range and turns O(n²) into O(n).
If the input is sorted, two pointers find a pair with a target sum or merge two sequences in linear time. For "longest substring without repeated characters" or "maximum sum of k neighbours", I keep a left and a right index and a Map of counts, and I move the window instead of recomputing the range. The hint is the word "contiguous" or "subarray". Then I think about a window before I write nested loops.
Два указателя — отсортированные массивы и пары; скользящее окно — непрерывные подстроки/подмассивы с состоянием, O(n²) → O(n).

How do you walk a tree like the DOM, and what is the difference between BFS and DFS?
DFS goes deep first, with recursion or an explicit stack; good for subtree problems. BFS goes level by level with a queue; finds the closest match. Both are O(n).
Recursive DFS is how React renders a tree. I use it to flatten a tree, to search a subtree or to compute depth. Deep trees can overflow the call stack, so a version with an explicit stack is safer. BFS uses a queue and visits the nearest nodes first, which answers questions like "the closest element with this class" or level-order rendering. For the real DOM there is TreeWalker, but on a whiteboard I write the loop myself.
DFS — вглубь (рекурсия или стек), для подзадач по поддереву; BFS — по уровням через очередь, ближайшее совпадение. Глубокие деревья — явный стек вместо рекурсии.

Explain memoization vs dynamic programming with a frontend example.
Memoization caches the results of a pure function, top-down. Dynamic programming fills a table from small subproblems, bottom-up. Example: edit distance for fuzzy search.
Memoization is what useMemo and reselect do: cache by input and reuse. In algorithms it turns an exponential recursion, like Fibonacci or edit distance, into polynomial time. Dynamic programming is the same idea written as a loop over a table. It avoids deep recursion and often needs only one row of memory. Fuzzy matching in a command palette and diffing two lists are everyday places where this matters.
Мемоизация — кэш результатов сверху вниз; DP — таблица снизу вверх, без глубокой рекурсии. Примеры: fuzzy-поиск (edit distance), диффы списков.

How do you implement an LRU cache, and where would you use it in a frontend?
A Map keeps insertion order. On get, delete and set the key again to make it the newest. On set over capacity, delete the first key. Both are O(1). Use it for bounded caches of results, images or parsed documents.
A JavaScript Map remembers the order of insertion. To mark a key as recently used, I delete it and set it again, so it moves to the end. The oldest key is map.keys().next().value. This gives a clean O(1) LRU cache in about fifteen lines, and it is a common live-coding task. In real life I use it to limit a client cache of search results, parsed documents or thumbnails, so memory does not grow forever.
Map хранит порядок вставки: get — удалить и вставить снова, set сверх лимита — удалить первый ключ, O(1). Для ограниченных кэшей результатов поиска, картинок.

What is the complexity of common array methods, and how do you avoid accidental O(n²) in React code?
includes, indexOf, find, splice and unshift are O(n). find inside map, sorting inside render, and unshift in a loop are the usual quadratic traps. Build a Map or an index once.
If a list renders rows and each row calls users.find(u => u.id === row.userId), that is O(n·m) on every render. A Map built once with useMemo makes it O(n). Sorting or filtering inside render without useMemo repeats O(n log n) work on every key press. unshift and splice at the start are O(n), so building an array by adding to the front in a loop is quadratic. I say these complexities out loud while coding, so the interviewer sees that I think about scale.
find внутри map, сортировка в рендере, unshift в цикле — скрытое O(n²). Строить Map/индекс один раз через useMemo и называть сложности вслух.
